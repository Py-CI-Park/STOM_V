## 0. 결론 (먼저)

**판정: 변환 필요(즉시 가능에 근접). 차단 요소는 1건뿐이다.**

리포트의 v5.0 복합 매수/매도 조건식은 STOM 엔진 네임스페이스와 **거의 완전히 호환**된다. 실증 검증 결과:

- **`compile()` 통과**: 매수(305줄)·매도(199줄) 두 블록 모두 문법 오류 없음. → PR2 워크벤치 `POST /bt/strategy/validate`를 **원문 그대로 통과**한다.
- **심볼 0건 미상**: AST로 추출한 모든 자유 식별자가 (a)기본 스칼라, (b)SetGlobalsFunc 화이트리스트 181함수, (c)매도전용 잔고변수, (d)조건식 내부에서 직접 계산하는 파생변수, (e)파이썬 내장(`max`/`min`/`int`/`round`) 중 하나로 100% 분류됨. **환각된 변수 없음.**
- **함수 인자 arity 일치**: `이동평균(60,1)`·`누적초당매수수량(10)`·`횡보감지(30,0.50)`·`호가갭발생(3)`·`구간고가대비현재가등락율(10)` 등 모든 함수 호출이 실제 시그니처와 일치.
- **`max()`/`min()` 사용 가능**: 실전략 88건 중 8건이 이미 `max`/`min`을 사용 → 내장 함수가 exec 네임스페이스에서 살아있음을 실증. 리포트의 `max(2, 최대위험점수-1)`·`min(최대보유시간,70)` 정상 작동.

**유일한 차단 요소(반드시 변환):** 조건식 말미의 주문 호출.
리포트는 `self.Buy(종목코드, 종목명, 매수수량, 현재가, 매도호가1, 매수호가1, 데이터길이)`(7인자)를 쓰는데,
백테스트 엔진 메서드는 `Buy(self, buy_long=False)`(인자 0~1개)다. 7인자 호출은 **런타임 TypeError**로 크래시한다(실측 확인).
자동발굴 루프(`band_compiler.py`)와 조건빌더(`GetBuyConds`)가 쓰는 **정식 footer는 `self.Buy()`(무인자)** 이며, 이 형태는 정상 실행된다(실측 확인).

→ **조치: 매수 말미를 `if 매수:\n    self.Buy()`, 매도 말미를 `if 매도:\n    self.Sell()`로 교체하면 즉시 백테 가능.** 그 외 본문은 한 글자도 바꿀 필요가 없다.

> 주의: 7인자 `self.Buy(...)`는 strategy.db 실전략 88건 중 19건이 동일하게 쓰고 있는 **레거시 라이브 트레이딩 관용구**다(라이브 strategy 클래스 계열에서 유래). 그러나 백테스트 엔진/조건빌더/자동발굴 루프의 canonical 형태는 모두 무인자 `self.Buy()`이며, **백테스트 실행 경로에서는 무인자 형태만 안전**하다.

`초소형주(<1500)·소형주(1500~5000)·중형주(5000~20000)·대형주(≥20000)` 4구간 × 시간대(시초초반/종료전) 보정으로

### 1.5 self.vars 최적화 체계 (50개)

`self.vars[0]=평균틱수(고정30)`, `[1~24]=매수`, `[25~39]=매도`, `[40~49]=자동발굴 메타`.
형식 `self.vars[i] = [[min, max, step], default]`는 strategy.db `stockoptivars` 포맷과 동일(실전략 대조 확인). **단, 본문 조건식은 동적 기준값을 if/elif 하드코딩으로 쓰므로, self.vars를 실제로 묶으려면 조건식 내 임계 리터럴을 `self.vars[i]` 참조로 치환하는 별도 최적화판이 필요**하다(1차 적용에는 불필요, 4단계 이후 과제).

### 2.2 발견한 호환성 문제: 총 1건 (+ 주의 2건)

**차단 1건:**
1. **`self.Buy(...)`/`self.Sell(...)` 7인자 호출** — 백테스트 엔진 `Buy(self, buy_long=False)`(`backengine_base.py:791`, `backengine_base_oms.py:87`)는 위치인자 0~1개만 허용. 7인자 호출 시 `TypeError: Buy() takes from 1 to 2 positional arguments but 8 were given`(실측). `GetBuyStg`(`back_static.py:144`)는 주석만 제거하고 `self.Buy(...)` 라인을 그대로 compile하므로 런타임에 도달해 크래시한다.
   - **근거**: 자동발굴 루프 `band_compiler.py:191` 및 조건빌더 `GetBuyConds`(`back_static.py:180`)는 모두 `if 매수:\n    self.Buy()`(무인자) 생성. 실측 시 무인자는 정상 실행.
   - **변환**: 매수 말미 → `if 매수:\n    self.Buy()`, 매도 말미 → `if 매도:\n    self.Sell()`.

**주의 2건(차단 아님, 1차 백테에서 실측 검증):**
2. **시가총액 단위** — 임계 1500/5000/20000의 단위(억/백만 등)가 엔진 스칼라와 다르면 시총 분기가 한쪽으로 쏠린다. 1차 짧은 백테에서 시총 구간별 거래분포로 즉시 확인.
3. **compile() 검증의 한계** — 워크벤치 `_compile_check`(`backtest_api.py:153`)는 **문법(SyntaxError)만** 본다. 심볼 실재·인자 arity·화이트리스트는 검증하지 않는다. 따라서 7인자 `self.Buy(...)`도 `/strategy/validate`는 통과하고 **백테 런타임에서야 실패**한다. → 반드시 짧은 백테(3단계)로 런타임 검증할 것.

> 참고로 화이트리스트 강제(AI 에이전트 생성 경로의 `forbidden.md` (c)항)는 **워크벤치 직접 등록 경로에는 적용되지 않는다**. 워크벤치는 순수 `compile()` 문법 검사만 하므로, 실재 심볼만 쓴다면 통과한다(본 리포트 조건식은 실재 심볼만 사용함을 §2.1에서 입증).

### 2.3 매수전략 금지변수(forbidden.md (a)) 준수 확인

리포트 매수식은 수익률·최고수익률·보유시간 등 **잔고변수를 일절 사용하지 않음**(AST 확인). 매도전용 동적청산 복합조건(`횡보상태장기보유` 등)도 매수식에 없음. → forbidden.md (a)항 위반 0건. 매도식에서만 잔고변수 사용(정상).

## 3. strategy.db 적용 방안

### 3.1 네이밍 (충돌 회피 확인 완료)

strategy.db `stockbuy`/`stocksell`의 `index`(이름) 컬럼을 전수 조회한 결과 `ORDERFLOW_V5_*` 접두 **충돌 0건**. 제안 네이밍:

| 역할 | 이름(`index`) | 테이블 |
|---|---|---|
| 매수(원문, 7인자 그대로) | `ORDERFLOW_V5_BUY_RAW_v1` | stockbuy |
| 매수(호환 변환판, 무인자) | `ORDERFLOW_V5_BUY_COMPAT_v1` | stockbuy |
| 매도(원문) | `ORDERFLOW_V5_SELL_RAW_v1` | stocksell |
| 매도(호환 변환판) | `ORDERFLOW_V5_SELL_COMPAT_v1` | stocksell |
| 최적화 변수판(후속) | `ORDERFLOW_V5_BUY_OPTI_v1` / `..._SELL_OPTI_v1` | stockoptibuy/sell + stockoptivars |

규칙: `ORDERFLOW_V5_<역할>_<상태>_v<n>`. 역할∈{BUY,SELL}, 상태∈{RAW,COMPAT,OPTI}.

### 3.2 등록 방식 (PR2 워크벤치 API)

대상 DB는 운영 `_database/strategy.db`(테이블 `stockbuy`/`stocksell`, 컬럼 `index`=이름, `전략코드`=코드). 엔드포인트(`backtest_api.py`, prefix `/bt`):

1. **문법 검증(저장 없이)**: `POST /bt/strategy/validate`  body `{"code": "...전략코드..."}` → `{ok, error?}`. compile() 문법만 검사.
2. **등록/수정**: `POST /bt/strategy`  body `{"kind":"buy"|"sell", "name":"ORDERFLOW_V5_BUY_COMPAT_v1", "code":"...", "overwrite":false}`.
   - compile() 통과 후 `DELETE+INSERT`(멱등). 동일 이름 존재 + `overwrite=false` → `{"status":"error","code":"exists"}`(HTTP 200, 무예외 컨벤션). 갱신은 `overwrite=true`.
   - 이름에 `\x00`/`\n`/`\r` 금지.
3. **삭제(필요 시)**: `POST /bt/strategy/delete`  body `{"kind","name","confirm":<이름과 동일>}`(이름 재입력 필수).
4. **데이터 범위 조회**: `GET /bt/data_range` → tick/min 일일 DB 날짜 목록 + back.db 보유기간.
5. **백테 실행**: `POST /bt/run`  body `{"buy":"ORDERFLOW_V5_BUY_COMPAT_v1","sell":"ORDERFLOW_V5_SELL_COMPAT_v1","start":YYYYMMDD,"end":YYYYMMDD,"timeframe":"tick","engines":4,"timeout":600,"one_code":"<선택>"}` → `{job_id}`. 잡 매니저가 `stom_backtest.py --format json` subprocess로 실행.
6. **상태/결과/분석**: `GET /bt/job?job_id=`, `GET /bt/result?...`, `GET /bt/analysis/{summary|equity|distribution|heatmap|underwater|insights}`.

### 3.3 단계적 적용 절차 + 합격 기준

| 단계 | 작업 | 합격 기준 |
|---|---|---|
| ① 원문 등록 시도 | `..._RAW_v1`을 `POST /bt/strategy`로 등록 | **compile() 통과 예상**(문법 OK 실측). 통과하면 "문법 호환 확정". 단, 백테는 7인자 `self.Buy`로 런타임 실패 예상 |
| ② 호환 변환판 작성 | RAW에서 footer만 무인자로 치환 → `..._COMPAT_v1` 등록 | compile() 통과 + §3.1 네이밍 무충돌 |
| ③ 짧은 기간 tick 백테 | `POST /bt/run` `timeframe=tick`, 1~3일, `one_code` 1종목 권장 | 잡 상태 `done`, **TypeError/NameError 0건**(잡 로그 테일 확인), 진입/청산 거래 ≥1건 발생, 시총 구간별 거래분포로 **시가총액 단위 정합성 확인** |
| ④ 전체 기간 검증 | `POST /bt/run` 전체 보유기간(`/bt/data_range`), engines=4 | 잡 완료, 분석 6종 정상 산출. 리포트 §5.3 목표(매매성능지수≥1.25, MDD≤4%, 일평균거래 6~20회, 평균보유 120~300초)와 대조 |

> RAW 등록(①)은 "문법 호환 증명 + 레거시 형태 보존" 목적의 기록용. **실제 백테/분석은 COMPAT 판으로만** 수행한다.

### 3.4 F01~F20 개별 추적 로그 설계 (리포트 §5 연계)

조건식은 이미 `복합점수`·`위험점수`·`전략플래그수`·`매수사유`(F01|F02|... 문자열)·`매도사유`·`세력이탈점수`·`방어실패점수`를 **로컬 변수로 계산**한다. 그러나 STOM 백테 결과 스키마는 이 로컬 변수를 자동 보존하지 않으므로, 플래그별 기여도(Lift/Expectancy)를 뽑으려면 **둘 중 하나** 필요:

- **방안 A(권장, 비침습)**: 진입 시점 스냅샷 저장 훅 활용. `backengine_base.Buy()`가 호출하는 `self._store_buy_snapshot(vturn, vkey)`(행819)가 진입 당시 배열을 저장한다 → F01~F20·복합점수·위험점수를 진입 스냅샷 컬럼(또는 매수사유 문자열)으로 남기도록 **별도 PR에서 스냅샷 컬럼 확장**. 리포트 §10 진입/청산 로그 스키마가 목표 스펙.
- **방안 B(분석 단계 재구성)**: 백테 거래기록(진입 시각·종목·가격)을 받아 동일 tick DB로 진입 시점 F01~F20을 **사후 재계산**하는 `trade_log_analyzer.py`(리포트 §15 제안 파일). 조건식 수정 불필요.

1차 적용에는 둘 다 불필요(조건식은 점수를 내부적으로 이미 계산). 기여도 분석을 본격화하는 시점(리포트 §11 Attribution Mode)에 방안 A를 우선 채택 권장.
