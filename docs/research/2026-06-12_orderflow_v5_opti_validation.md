## 2. 변환 방식 (게이트 호이스팅)

```
# OPTI 골격 (실제 구조)
매수 = False                       # 게이트 미통과 tick 의 기본값(= COMPAT 가 게이트 분기로 도달하는 값)
if 90005 <= 시분초 < 92800:
    <COMPAT 본문 1~248줄(파생변수~최종판단부)을 4칸 들여쓰기로 그대로 이식>   # 1글자 무변경
                                   # ← 이 블록 안에 COMPAT 의 `매수 = True`/내부 게이트/`else: 매수=False` 가 모두 그대로 포함됨
if 매수:                           # footer 는 top-level 유지
    self.Buy()
```

- 호이스팅한 게이트 = COMPAT E구간 첫 분기의 조건식 `90005 <= 시분초 < 92800` (원문에서 확인한 '매수 가능 시간창 전체'). 시초초반/장초1·2·3/종료전의 세부 동적 게이트는 본문에 그대로 남겨 둠 → 1차 게이트는 가장 바깥 창만 차단.
- 게이트 밖 처리는 **최상단 `매수 = False` 한 줄**로 갈음(별도 `else` 불필요). COMPAT 본문의 `매수 = True`(191줄)·내부 `if not (90005 ...): 매수 = False`(192–193줄)·말미 `else: 매수 = False`(247–248줄)는 게이트 안에 **바이트 그대로 보존**(게이트 안에선 내부 게이트가 항상 거짓이라 무해).
- 주문 footer `if 매수:` + `self.Buy()` 는 최상단 게이트 밖(top-level)에 유지 → 게이트로 걸러진 tick은 `매수=False` 이므로 미발주.

## 4. 매도 OPTI 검토 결정 — COMPAT 재사용

**결정: 매도는 호이스팅하지 않고 COMPAT 그대로 사용한다.** 근거:

1. **평가 빈도가 낮다.** 엔진은 매도식을 보유 중(`else` 분기)에만 `exec(self.sellstg)` 한다. 진입은 09:00:05~09:28:00 에만 발생하고, 보유시간은 시총별 60·90·150·240초 상한(+시초/종료전 추가 단축)으로 짧다. 따라서 매도식이 도는 총 tick 수는 하루 전체의 극히 일부.
2. **단축 가능한 유휴창이 없다.** 매도식 최상단 시간 분기는 `시분초 >= 92900`(시간강제청산)·`시분초 < 90200`·`시분초 >= 92000`(파라미터 보정)으로, 보유 중이면 시각과 무관하게 손절·트레일링·세력이탈/방어실패 점수 청산을 **매 tick 평가해야** 한다. 매수처럼 "이 시간대엔 어차피 거래 안 함" 식의 큰 건너뛸 구간이 존재하지 않는다.
3. **위험 회피.** 매도 로직은 청산 안전장치다. 들여쓰기 재배치로 미세 의미 변화를 유발할 위험을 감수할 이득이 없다.

→ 매도식 경량화는 비용 대비 이득 없음·리스크 있음으로 기각. COMPAT 재사용이 보수적·정합적.

## 5. 실증 백테 (단계적)

### 5.0 진단: `engine_data_response_timeout` 은 전략이 아니라 데이터 로딩 단계 ✕

첫 OPTI Stage① 실행(`...83107`)이 627s 에 `error / exit=3 / engine_data_response_timeout` 으로 종결됐다. 이 체크포인트(`cli/runner.py:_collect_engine_shared_info`)는 **엔진 워커가 종목 tick 배열을 로딩해 `backQ` 로 회신하기를 기다리는 단계**로, **전략 exec 이전**이다. 즉 OPTI 매수식 자체와 무관하다.

이를 증명하기 위해 **동일 config(009830/20260227/tick/한종목 로딩/engines=1/동일 override)**로 단순 대조전략 `WEBBT_SMOKE_ALWAYS_B/S` 를 실행 → **58.3s 에 success, 133거래** 정상 산출. config·override·데이터 경로는 정상임이 확인됐다.

결론: 첫 OPTI 실패는 **warm-session 엔진의 데이터 로딩 회신 지연(콜드/경합성)** 이며 전략 무관. (참고: #10 도 v5 multi-code 에서 동일 단계 교착을 관찰, "전략 무관 코드 경로" 의심을 기록.) → warm-session 정상화 후 OPTI 재실행으로 실제 성능을 측정한다(아래 5.1).

### 5.1 단계 ① — 1종목(009830)·1일(20260227)·tick·engines=1·tick_subset override

**핵심 해석(정직한 결과 — 경량화는 부분적, 1종목 1일 tick 완주 실패):**

- **OPTI 1종목 1일(009830/20260227) tick 은 600s 도, 1500s 도 완주하지 못했다.** 게이트 호이스팅으로 게이트 밖(정규장 ~6.5h 의 ~93%) tick 을 전부 건너뛰는 구조는 검증됐지만, **매수 가능창(09:00:05~09:28:00, ~28분)의 고밀도 tick 에서는 A구간(파생변수)+C구간(F01~F20 롤링 다수)이 여전히 매 tick 전부 실행**된다. 009830 같은 거래대금 상위 종목의 개장 직후 28분은 tick 밀도가 극히 높아, 게이트 안 연산만으로도 1500s 를 초과한다.
- **경량화가 실재한다는 증거 = "실패 지점의 전진".** 두 실패 모드는 질적으로 다르다:
  - COMPAT(#10) 및 OPTI 1차(cold)는 **데이터 로딩/이른 단계**에서 막혔다.
  - OPTI 2차·3차(warm)는 **데이터 로딩을 통과해 `backtest_process_started`(전략 실행 단계) 진입 후** 시간초과로 종료 — 즉 OPTI 는 매번 전략 exec 까지 도달하며, COMPAT 보다 더 멀리 진행한다.
  - 다만 **절대 완주 시간 측정은 불가**(1500s 로도 미완). 따라서 "경량화 배율 실측치"는 본 실증으로 산출되지 않으며, 산출하려면 더 가벼운 부하(아래)가 필요하다.
