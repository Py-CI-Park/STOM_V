## 3. E1 — timeout 원인

### 관측

- 기준선: worker completed
- 교정 전 G2: 5개 worker 모두 첫 전략 실행에서 `NameError`
- parent: worker 오류를 받지 못하고 첫 MQ heartbeat를 계속 기록

### 결합 원인

1. G2 renderer가 `VI아래5호가`를 선언하지 않았다.
2. `BackStop(3)`가 parent `tq`에 중지 메시지를 보내지 않았다.
3. 이 때문에 실행 오류가 300초 timeout으로 위장됐다.

### 교정

```python
VI아래5호가 = VI가격 - VI호가단위 * 5
```

- 전략 예외에 worker ID·code·index·오류줄 receipt 추가
- worker 오류를 parent에 즉시 전파
- 운영 DB 대신 명시적 연구 sidecar DB 사용

### 재현

교정 G2는 공식 엔진에서 3/3 success, 실제 worker 15/15 completed였다. E0의 “엔진이 단순 조건식을 못 돈다”는 해석은 폐기됐다.

## 4. E2 — STOM source 실행계약

`execution_contract.py`가 엔진 전에 다음을 검사한다.

- canonical AST 구문·unknown line
- 허용 함수
- lookback·절 수·estimated work
- stock tick runtime symbol
- 파생변수의 사용 전 top-level assignment
- no_adoption 권위

교정 전 G2는 `undefined_runtime_symbol`, 교정 G2는 work 10.0·undefined 0으로 통과했다.

이것은 STOM 문법이나 엔진 계산을 교체하는 구조 변경이 아니다. 기존 source와 engine 사이에 fail-closed research control plane을 추가한 것이다.

## 7. 연구가 의미 있었는가

### 의미 있는 성과

1. timeout의 진짜 원인을 코드·runtime symbol 수준에서 특정했다.
2. 오류가 timeout으로 위장되는 엔진 관측 결함을 제거했다.
3. 생성 source 12개를 정적 계약→공식 엔진→Pareto→MAP-Elites로 연결했다.
4. 5일 양수 후보를 즉시 temporal folds에서 반증했다.
5. Bayesian `CONTINUE`를 승인으로 포장하지 않았다.
6. BOOK/FLOW는 2023-06 의존, MOMENTUM은 현재 범위에서 폐쇄라는 지식을 얻었다.
7. 다음 연구가 같은 데이터·같은 문턱을 반복하지 않도록 증거를 남겼다.

### 경제적 성과

실전으로 승격할 조건식은 0개다. 연구의 경제적 직접 성과는 아직 없다.

### 비용 절감 성과

앞으로 미정의 변수 후보는 300초 timeout까지 기다리지 않고 엔진 전에 거부된다. worker 전략 예외도 parent에 즉시 전달된다.
