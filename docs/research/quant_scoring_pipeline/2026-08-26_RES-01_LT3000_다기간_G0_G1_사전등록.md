## 1. 이 문서가 봉인하는 것

이 문서는 `<3000억` Band의 G0 Event 추정·공식 다기간 개발 실행·구조 부검·G1 재실행을 시작하기 전에 입력과 판정 규칙을 고정한다. 동반 기계가독 manifest는 `evidence/2026-08-26_res01_lt3000_prereg.json`이다.

이 커밋보다 앞선 결과는 본 Batch의 결과가 아니며, 이 커밋 뒤에도 아래 규칙을 바꾸려면 기존 Batch를 중단하고 새 계약 ID로 다시 사전등록해야 한다.

## 2. 연구 질문과 주장 경계

| 질문 | 이번 Batch가 답할 수 있는 것 | 답할 수 없는 것 |
|---|---|---|
| 5개 상태전이 Family가 여러 개발 구간에서 충분히 발생하는가 | Event count·날짜·종목 분산 | 수익성·OOS |
| 공식 STOM 엔진에서 재현 가능한가 | source match·terminal·failure cause | 실전 체결 가능성 |
| 구조 개선 G1이 G0보다 나아지는가 | 동일 개발 fold의 paired 변화 | 새 데이터 일반화 |
| 개발 후보가 있는가 | 사전등록 development rule | Robust/OOS/실전/자동채택 |

성공 단어는 다음처럼 제한한다.

| 용어 | 필요한 증거 |
|---|---|
| 실행 성공 | 공식엔진 success + source match + 완전한 artifact |
| 개발 Rule-pass | 4개 개발 fold의 사전등록 경제 기준 |
| 구조 개선 | paired G0→G1 개선 기준; Rule-pass와 별개 |
| Robust | RES-04 controls·BH-FDR·posterior·tick2 gate |
| OOS | 후보·코드 봉인 후 별도 승인된 2026 holdout 1회 |

## 5. 개발 Fold와 봉인 Holdout

성과를 보지 않고 DB coverage 달력만으로, coverage 첫 완전 분기 Q2부터 해마다 분기를 한 칸씩 이동시키고 그 분기의 첫 달을 선택했다.

| Fold | 기간 | 역할 |
|---|---|---|
| `DEV_2022_Q2_MONTH1` | `2022-04-01~2022-04-30` | development |
| `DEV_2023_Q3_MONTH1` | `2023-07-01~2023-07-31` | development |
| `DEV_2024_Q4_MONTH1` | `2024-10-01~2024-10-31` | development |
| `DEV_2025_Q1_MONTH1` | `2025-01-01~2025-01-31` | development |
| Frozen holdout | `2026-01-01~2026-02-27` | **봉인·RES-02/03 접근 금지** |

네 기간은 모두 development다. 과거 다른 연구가 일부 날짜를 사용했을 가능성을 숨기지 않으며 새 OOS라고 부르지 않는다. 실제 DB에서 한 Fold의 거래일이 15일 미만이면 날짜를 바꾸지 않고 `SOURCE_COVERAGE_UNAVAILABLE`로 중단한다.

## 6. 실행 전 필수 Gate

아래가 하나라도 미완료면 Event 측정 또는 공식 실행을 시작하지 않는다.

| Gate | 통과 증거 | 실패 행동 |
|---|---|---|
| DB identity | size + sampled fingerprint 일치, read-only open | 새 Census 전 중지 |
| manifest identity | file/canonical/window hash 일치 | 중지 |
| 160 source identity | 각 source SHA-256 일치 | 중지 |
| 정적 계약 | syntax·허용 변수·lookback·work·모순 검사 | 후보별 typed 제외 |
| 이전 TypeError | 두 FAILED_BREAKOUT 후보의 red→green counterexample receipt | 공식 실행 전체 중지 |
| 엔진 계약 | commit/tree/config hash와 비용 정책 기록 | 중지 |
| 작업 격리 | manager별 독립 jobs dir | 중지 |
| 보호 경로 | DB·로그·graph 등 변경 0 | 즉시 중지 |

과거 `FAILED_BREAKOUT_RETURN` 두 후보는 `006740`의 2023-11-14 tick에서 `list indices must be integers or slices, not str`가 났다. traceback 없는 추정만으로 고쳤다고 선언하지 않는다. 실제 반례 또는 동등한 최소 fixture를 먼저 RED로 재현하고 GREEN을 확인해야 한다.

## 7. Event Gate

Event estimator 입력은 candidate/fold/day/symbol/timestamp/triggered만 허용한다. 수익·수익률·MDD·승률·미래가격·청산 결과는 schema 차원에서 거부한다.

| 기준 | 값 |
|---|---:|
| 전체 Event | 200 이상 |
| 각 개발 Fold Event | 20 이상 |
| distinct days | 20 이상 |
| distinct symbols | 10 이상 |
| 누락 Fold | 0으로 계산 |

통과 후보가 2개보다 많아도 Event 수가 많은 순서로 뽑지 않는다. Family 안에서 parameter 공간의 거리를 최대화하는 2개만 뽑는다. 이 단계에서 후보가 0이면 `STOP_NO_EVENT_QUALIFIED_G0_CANDIDATE`로 정상 종료한다.

## 9. 비용·경제 기준

| 계층 | 가정 |

### 9.2 Development Rule-pass

| 기준 | 값 |
|---|---|
| execution/source | 4/4 success + exact source match |

실행 실패는 음수 성과로 바꾸지 않고 `NOT_EVALUABLE`로 남긴다. 위 기준 통과도 development 권위일 뿐 Robust가 아니다.

## 10. G0→G1 자율 개선 계약

G1은 G0 결과를 이용하는 적응형 development 단계다. 따라서 같은 Fold에서 나아져도 일반화 성공으로 부르지 않는다.

| 허용 | 금지 |
|---|---|
| 상태 순서 변경 | winner 주변 threshold 소폭 조정 |
| 논리 역할 추가/제거 | 양수 parent만 선택 |
| 진입/청산 책임 재분리 | 좋은 달·좋은 거래만 사용 |
| PnL 비사용 실행비용 축소 | Band·기간·비용 변경 |

유효 실행된 모든 G0 parent에 동일한 Family 구조 가설을 적용한다. 음수 parent도 제외하지 않는다. G1도 같은 4개 Fold·비용·엔진 identity로 최대 40 jobs를 실행한다.

paired 개선은 `median fold average-profit delta > 0`이면서 `worst-fold total-profit delta >= 0`일 때만 `IMPROVED`다. 이 판정과 Development Rule-pass는 별도다. 이번 파일럿은 G1에서 끝나며 결과 후 G2를 추가하지 않는다.

## 11. 구조 분석과 Robust Gate

G0/G1 분석은 모든 거래·무거래·오류·timeout을 포함해 Family별로 수행한다. 분석 순서는 실행 완전성 → 표본 → 분포 → 시간/종목 episode → 진입/청산 귀속 → 비용 민감도 → paired 변화다.

Development Rule-pass 후보만 RES-04로 보낸다. RES-04에서 timestamp shuffle, symbol shuffle, direction inversion, same-event random offset, parameter-random baseline을 실행하고 `BH-FDR q<=0.10`, `P(expectancy>0)>=0.95`, `tick2 total profit>0`을 모두 만족해야 `BO_ELIGIBLE`이 될 수 있다.

## 12. 중지 규칙

| 중지 code | 의미 | 다음 행동 |
|---|---|---|
| `STOP_SOURCE_OR_MANIFEST_IDENTITY_MISMATCH` | 입력 정본 불일치 | 새 Census/계약 검토 |
| `STOP_FAILED_BREAKOUT_RUNTIME_PARITY_UNRESOLVED` | 과거 TypeError 미해결 | 디버깅 전용 브랜치 |

| `STOP_VALID_EXECUTION_RATE_BELOW_0_8_AFTER_ONE_INFRA_RETRY` | 유효 실행률 80% 미만 | 플랫폼 실패로 종료 |
| `STOP_AFTER_G1_NO_DEVELOPMENT_RULE_PASS` | G1까지 개발 통과 0 | 경제 후보 없음으로 종료 |

## 13. 금지 사항

- 결과 후 시총 경계·Fold 날짜·비용·반복 수를 바꾸지 않는다.
- Event 통과 후보를 PnL로 순위화하지 않는다.
- 양수 parent만 G1으로 전달하지 않는다.
- threshold 미세조정을 구조 개선이라고 부르지 않는다.
- 2026 holdout을 후보·코드 봉인과 별도 인간 승인 전에 열지 않는다.
- development 결과를 OOS·실전·자동채택으로 표현하지 않는다.
- 전략 DB나 보호 DB에 쓰지 않는다.

## 14. RES-02 착수 조건

본 문서와 JSON manifest가 독립 Git commit으로 먼저 봉인된 뒤에만 RES-02 브랜치를 만든다. RES-02의 첫 작업은 백테스트가 아니라 DB/manifest/runtime counterexample preflight와 실제 Event estimator의 read-only 구현이다.

현재 worktree에 `_database/stock_tick_back.db`가 없으면 문서화된 identity를 합성하거나 빈 DB를 만들지 않는다. 이 경우 RES-02는 `NO-GO: DB_NOT_PROVISIONED`까지 진행하고 공식 실행은 멈춘다.
