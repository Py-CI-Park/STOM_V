## 2. 시가총액 분할 아이디어 판정

### 2.1 타당성

시가총액 분할 연구는 **타당하다**. STOM의 `시가총액` 단위는 억이며, Tick runtime과 매수시점 `B_시가총액`이 존재한다. 기존 코드에도 시간×시가총액 분석, 시총 band compiler, 초기 `<1000 / 1000~5000 / >=5000` 분류가 있다.

시총별로 다음이 구조적으로 달라질 수 있다.

- 체결 빈도와 호가 깊이
- 동일 거래대금 충격의 가격 탄력성
- VI·라운드피겨·갭 반응
- 돌파 유지시간
- 손절·익절·최대 보유시간
- 관심종목 편입 빈도와 표본 수

따라서 모든 종목에 같은 threshold를 적용하는 것보다 한 시총 층만 고정해 가설·변수·Exit를 연구하면 이질성이 줄고 원인 해석이 쉬워진다.

### 2.2 그대로 실행하면 생기는 위험

| 위험 | 설명 | 통제 |
|---|---|---|
| 표본 불균형 | 특정 band의 종목·거래일·신호가 부족할 수 있음 | 전략 생성 전 DB census |
| 경계 사후조정 | 성과를 보고 3000·5000·10000을 이동하면 과적합 | 경계 사전 봉인 |
| 다중검정 | 4 band×4 family×후보가 급증 | Family/band별 BH-FDR·trial ledger |
| 시총 변화 | 동일 종목이 날짜별로 다른 band가 될 수 있음 | 매수시점 `B_시가총액`으로 분류 |
| 유동성 혼입 | 시총 효과가 거래대금 효과일 수 있음 | Band 내부 유동성 기술통계·고정 gate |
| 생존편향 | 관심종목/DB 포함 종목만 존재 | Coverage 한계 표시, 전체시장 주장 금지 |
| 매우 큰 종목 희소성 | `>=10000`에서 opening signal이 적을 수 있음 | 최소 표본 미달 시 병합하지 않고 `INSUFFICIENT` |

### 2.3 사전등록할 Band

| Band ID | 시가총액(억) | 사용자 해석 | 경계 규칙 |
|---|---:|---|---|
| `MCAP_A_LT3000` | `< 3000` | 3000억 이하 | `시가총액 < 3000` |
| `MCAP_B_3000_5000` | `3000 <= x < 5000` | 3000~5000억 | 하한 포함·상한 제외 |
| `MCAP_C_5000_10000` | `5000 <= x < 10000` | 5000억~1조 | 하한 포함·상한 제외 |
| `MCAP_D_GE10000` | `>= 10000` | 1조 이상 | `시가총액 >= 10000` |

경계 누락·중복은 허용하지 않는다. Census에서 표본 부족이 확인돼도 성과를 본 뒤 경계를 이동하지 않는다. 해당 band는 `INSUFFICIENT_SAMPLE`로 남긴다.

## 6. C0 — 시가총액 Census

전략을 생성하기 전에 기존 DB 전체를 읽기 전용으로 조사한다.

### 6.1 집계

Band별로 다음을 계산한다.

| 축 | 지표 |
|---|---|
| Coverage | 거래일·종목·tick 수·첫/마지막 날짜 |
| 관심종목 | 일별 distinct 종목·편입 빈도 |
| 유동성 | 당일거래대금·초당거래대금 분위수 |
| Microstructure | 체결강도·잔량비·spread proxy 분위수 |
| 가격행동 | 등락율·고저폭·VI 발생·돌파 빈도 |
| 시간 | 5분 bucket별 표본·종목·event 수 |
| Stability | 연도·월별 band 비중 변화 |

### 6.2 최소 표본 Gate

| Gate | 최소 기준 |
|---|---:|
| Band coverage | 12개월 이상 |
| Distinct 거래일 | 120일 이상 |
| Distinct 종목 | 30개 이상 |
| Family별 사전 event | 전체 200회 이상 |
| Fold별 expected trades | 20건 이상 예상 |

미달 band는 전략 생성 없이 `INSUFFICIENT_SAMPLE`이다. 실제 Census 결과에 따라 기준의 실현 가능성은 보고하되 사후 성과를 보고 완화하지 않는다.

### 6.3 W0 — Census 기반 시간계약 이관

현재 확인된 `moneytop`은 최대 10:30을 포함할 수 있지만 일부 Tick 종목 테이블은 09:30까지만 관측됐다. D3는 C0에서 `moneytop`과 실제 종목 테이블의 공통 유효범위를 계산하고 그 결과를 lane별 시간계약으로 봉인한다.

- Tick 종목 coverage가 09:30까지면 Tick D3는 `09:00~09:30`만 사용한다.
- Min DB가 10:30 이후를 실제 제공하면 별도 Min lane 계약으로 분리한다.
- Tick과 Min 결과를 같은 Candidate/Family evidence로 합치지 않는다.
- 요청 범위에 실제 종목 row가 없으면 `SOURCE_COVERAGE_UNAVAILABLE`로 차단한다.

| Surface | 변경·검증 |
|---|---|
| Principle gate | 09:30 고정 상한 제거, 명시적 `window_contract` 소비 |
| Prompt/generator | Census가 봉인한 lane별 전체 가용범위를 표시 |
| Candidate renderer | `time_start/time_end`가 계약 범위 안인지 fail-closed |
| Forced exit | 연구 Exit의 강제청산 시간이 계약과 충돌하지 않음 |
| Event estimator | 동일 범위만 Count |
| BackFinder | lane별 동일 start/end time |
| Official runner | spec·receipt에 window contract hash 기록 |
| UI Data Scope | 실제 Census 범위와 계약 범위 동시 표시 |

기존 D1/D2 Evidence와 운영 기본값은 재해석하거나 덮어쓰지 않는다. D3 run profile에서만 새 시간계약을 명시적으로 선택한다.

## 7. D3 — 시총별 Opening State Machine

### 7.1 기존 연구와 차이

기존 방식:

```text
현재값 threshold A AND B AND C → 즉시 진입
```

D3 방식:

```text
상태 진입 → 최소 지속 → 사건 발생 → 확인 → 제한시간 내 진입
```

### 7.2 Family

| Family ID | 상태전이 가설 | 최대 차원 |
|---|---|---:|
| `ABSORPTION_REVERSAL` | 매도/매수압력 증가에도 가격 진행 제한→반대 Flow 전환 | 4 |
| `FAILED_BREAKOUT_RETURN` | Range 돌파→유지 실패→Range 복귀→반대 확인 | 4 |
| `COMPRESSION_CONFIRMED_BREAKOUT` | 변동성 압축 지속→확장→돌파 유지→확인 | 4 |
| `FLOW_PRICE_DIVERGENCE` | 체결 Flow와 가격반응 불일치 지속→해소 방향 진입 | 3 |
| `OPENING_OVERREACTION_MEAN_REVERT` | 시초 과잉변동→거래대금 둔화→극값 미갱신→중앙 회귀 | 4 |

모든 Family는 4개 시총 band 중 하나만 선택해 별도 전략으로 생성한다. 한 전략에 여러 band branch를 넣지 않는다. 이로써 어떤 band의 Edge인지 직접 식별한다.

### 7.3 Band별 가설 조정 원칙

| Band | 연구 초점 | 금지 |
|---|---|---|
| `<3000` | VI·급격한 Flow·짧은 유지 확인 | 단순 고체결강도 추격 |
| `3000~5000` | 돌파 유지·호가압력 전환 | `<3000` threshold 복사 |
| `5000~10000` | 압축·완만한 Flow 지속·실패 돌파 | 소형주 거래대금 배수 복사 |
| `>=10000` | 낮은 탄력성·흡수·Flow/가격 괴리 | 희소 신호를 성공으로 과장 |

이는 방향 가설이며 임계값은 Census 분위수에서 사전 산출한다.

Budget 숫자는 Census와 estimator 결과에 따라 **감소만** 가능하다. 성과를 보고 증가시키지 않는다.

## 9. Negative Controls

각 Family×Band에 동일한 거래 기회를 가진 대조군을 둔다.

| Control | 목적 |
|---|---|
| Timestamp shuffle | 시간 순서 우연성 검사 |
| Symbol shuffle | 종목 선택 우연성 검사 |
| Direction inversion | 방향 가설 검증 |
| Event-offset random entry | 동일 이벤트 수의 무작위 진입 |
| Parameter-random baseline | QMC 후보 우위 확인 |

후보가 대조군의 median·상위 분위수를 넘지 못하면 공식엔진 확대를 중지한다.

## 10. 개발 Fold 설계

현재 존재하는 DB만 사용하며 모든 구간을 development로 명명한다.

### 10.1 Nested 구조

| 역할 | 목적 |
|---|---|
| Inner discovery folds | QMC ranking·top-k 선택 |
| Outer confirmation folds | 선택된 후보의 시기 이동 확인 |
| Stress folds | 월별 급등락·저유동성 구간 진단 |

구체적 날짜는 C0에서 band별 coverage를 계산한 뒤, 성과를 보지 않고 달력·표본 수 기준으로 봉인한다. D1/D2/Paired에 이미 사용한 월은 provenance에 표시하고 새 OOS로 부르지 않는다.

### 10.2 Fold 성공 기준

- official engine `success`
- source snapshot match
- 거래 20건 이상
- 평균수익률 > 0
- 총수익률 > 0
- MDD <= 15%
- Negative control 대비 우위
- Family×Band 다중검정 FDR 통과 또는 Bayesian `APPROVE`

### 10.3 Family×Band 최종 판정

| 판정 | 조건 |
|---|---|
| `INSUFFICIENT_SAMPLE` | Census/event/trade 하한 미달 |
| `DEVELOPMENT_REJECT` | Rule 기준 실패 |
| `DEVELOPMENT_RULE_PASS` | deterministic 기준 통과, posterior 미승인 |
| `BAYESIAN_APPROVE` | posterior 기준까지 통과 |
| `BO_ELIGIBLE` | Rule+posterior+control 모두 통과 |

## 11. D4 — 저차원 Bayesian Optimization

BO는 `BO_ELIGIBLE` Family×Band cell에만 적용한다.

| 항목 | 제한 |
|---|---|
| 완성 전략 변수 | Entry 6~8 + Exit 4~6, 총 10~14개 허용 |
| 한 단계 Active 변수 | 최대 8개 |
| Entry 탐색 | QMC 32~64 + TPE 최대 24 |
| Exit 탐색 | QMC 24~48 + TPE 최대 16 |
| Joint local refinement | Entry 2 + Exit 2, 최대 4개·16~24 trial |
| 초기 관측 | 사전등록 QMC·Native inner 결과 |
| Acquisition | TPE/Expected Improvement 계열, Random 대조 |
| 평가 | Multi-fidelity inner → rolling development → 봉인 outer |
| 시간 Budget | 전체 Native search 24시간 목표, 최대 48시간 hard stop |
| 중지 | 6회 연속 개선 없음, resource/error budget 초과, gate 실패 |
| 권위 | development/no adoption |

변수 최대 3개 제한은 폐기한다. 상태전이 Entry는 상태 window·지속시간·event threshold·확인 window·가격반응·유동성·시간 제한 등 6~8개가 자연스럽고, Exit도 손절·익절·최대보유·trailing·flow exit 등 4~6개가 필요하다.

다만 10~14개를 동시에 최적화하지 않는다. 완성 전략은 많은 변수를 가질 수 있지만 한 탐색 단계에서 움직이는 Active 변수는 최대 8개로 제한하고 Entry→Exit→작은 Joint refinement 순서로 최적화한다.

Band 경계 3000·5000·10000은 BO 대상이 아니다. 경계까지 최적화하면 시총 분할 가설이 사후 조정되므로 고정한다.

## 11A. STOM Native 백파인더·최적화·Rolling Walk-Forward 통합

### 11A.1 판정

STOM에 이미 존재하는 백파인더·조건최적화·일반 변수최적화·유전알고리즘·Rolling Walk-Forward를 재출발 연구에 활용하는 것은 **타당하고 권장한다**. 다만 이 도구들은 모두 같은 단계에서 같은 권한으로 사용하지 않는다.

| Native 도구 | 현재 기능 | D3 역할 | 경제적 판정 권한 |
|---|---|---|---|
| `BackFinder` | `self.tickcols/self.tickdata` event snapshot 수집 | C0 Census·Event estimator·분위수 탐색 | 없음 |
| `OptimizeConditions` | 조건 조합 Train/Valid 평가 | 고정 Family×Band 내부 조건 절 선택 | Inner discovery only |
| `Optimize` | `self.vars[i]` 범위·Optuna sampler 최적화 | D4 적격 Cell의 Entry 6~8·Exit 4~6 단계별 조정 | Outer fold 전까지 없음 |
| `OptimizeGeneticAlgorithm` | 조건/변수 조합 유전 탐색 | 보조 탐색·구조 후보 제안 | 없음 |
| `RollingWalkForwardTest` | Train/Valid/Test rolling 최적화 | Nested development 실행·안정성 확인 | Development only |

### 11A.2 직접 사용 전 필수 격리

현재 Native 도구는 기본적으로 `DB_STRATEGY`, `DB_BACKTEST`, `DB_OPTUNA`, 설정 DB를 직접 참조하고 일부 최적화 결과를 strategy DB에 `UPDATE`한다. 본 계획의 운영 DB read-only 계약 때문에 그대로 실행할 수 없다.

`NativeResearchAdapter`를 먼저 구현한다.

```text
native_runs/<run_id>/
├─ strategy.db      # exact source·optibuy/optisell/optivars snapshot
├─ backtest.db      # native 결과 전용
├─ optuna.db        # study 전용
├─ setting.db       # 실행 설정 snapshot
├─ csv/             # 결과 전용
└─ receipt.json     # source/config/data/trial identity
```

필수 환경 경계:

- `STOM_CLI_DB_STRATEGY`
- `STOM_CLI_DB_BACKTEST`
- `STOM_CLI_BACKTEST_CSV_DIR`
- 별도 Optuna DB override
- 별도 Setting DB override
- Tick DB는 공용 Native read-only connector로 `mode=ro&immutable=1`

Adapter는 실행 전·후 운영 DB hash와 WAL/SHM 생성 여부를 검사한다. 운영 DB 변경 또는 Native 결과의 source hash 불일치가 발생하면 모든 성과를 무효화한다.

현재 Native 구현 일부는 Tick DB에 `sqlite3.connect(db)`를 직접 호출하므로 환경변수만으로 read-only를 보장할 수 없다. N0 구현에서 데이터 DB 연결을 공용 `connect_existing_db_readonly(path)`로 교체하고 URI `file:<path>?mode=ro&immutable=1`을 사용해야 한다. Strategy/Backtest/Optuna/Setting은 writable sidecar, 원본 Tick DB만 immutable read-only로 역할을 분리한다. 이 connector contract test가 통과하기 전에는 Native 도구를 실행하지 않는다.

### 11A.3 BackFinder 활용

BackFinder는 수익 최적화기가 아니라 조건 성립 시점의 설명변수 수집기로 사용한다.

Band×Family별 백파인더 전략:

```python
self.tickcols = [
    '시가총액', '시분초', '등락율', '체결강도',
    '초당거래대금', '당일거래대금',
    '매수총잔량', '매도총잔량',
    '상태지속틱', '상태전환종류'
]
self.tickdata = [...]
```

수집 목적:

| 목적 | BackFinder 산출물 |
|---|---|
| Band Census | Band별 event·종목·날짜·시간 분포 |
| 임계값 사전 산출 | 변수 분위수·상관·결측·극단값 |
| 상태전이 검증 | 진입→지속→사건→확인 단계 발생 수 |
| 희소성 차단 | Fold별 expected event/trade 수 |
| Negative control 설계 | 동일 Band·시간·event 수 대조군 |

BackFinder 결과는 후보 성과와 결합해 경계를 사후 변경하는 데 사용하지 않는다. Threshold 후보는 discovery fold에서만 산출하고 사전등록 후 고정한다.

### 11A.4 OptimizeConditions 활용

조건최적화는 Family의 경제 가설을 새로 발명하는 용도가 아니라, 이미 고정된 상태전이 단계에서 필요한 절을 선택하는 용도로 제한한다.

예:

```text
고정:
  MCAP_B_3000_5000
  FAILED_BREAKOUT_RETURN
  시간대 09:00~10:30

선택 대상:
  복귀폭 확인
  체결강도 반전
  잔량비 전환
  최소 유지 Tick
```

제약:

- Band 경계는 고정
- Family 변경 금지
- 후보 절 최대 10개
- 최종 활성 절 최대 5개
- Train/Valid에서만 조합 탐색
- 모든 조합 수를 trial ledger에 포함
- 선택 결과는 Outer fold에서 처음 평가
- Outer 결과를 보고 절을 다시 선택하지 않음

### 11A.5 일반 Optimize·Optuna 활용

STOM `Optimize`는 다음 sampler를 지원한다.

- `QMCSampler`
- `TPESampler`
- `CmaEsSampler`
- `RandomSampler`
- `BruteForceSampler`

D3/D4 사용 순서:

| 순서 | Sampler | 용도 | Budget |
|---:|---|---|---:|
| 1 | QMC | 적격 Cell의 초기 균일 피복 | Entry 32~64, Exit 24~48 |
| 2 | TPE | 중차원 국소 개선 | Entry 최대 24, Exit 최대 16 |
| 3 | QMC/TPE | Entry 2+Exit 2 joint local refinement | 16~24 |
| 보조 | Random | Null/search-bias 대조 | 각 단계 Trial의 25% 이상 |
| 금지 기본 | BruteForce | 조합 폭증 위험 | 작은 이산공간 증명 시만 |
| 금지 기본 | CMA-ES | 표본·trial 부족 | 충분한 연속공간 근거 없이는 사용 안 함 |

최적화형 조건식은 Native 계약을 사용한다.

```python
self.vars[0] = [[low, high, step], default]
```

원칙:

- 완성 전략 변수는 Entry 6~8, Exit 4~6 허용
- 한 단계 Active 변수는 최대 8개
- 범위는 Census/BackFinder discovery 분위수에서 봉인
- Default는 이미 Rule-pass한 값
- 시총 경계는 변수화하지 않음
- 전체 Buy/Exit 동시 최적화는 금지하되, 단계별 최적화 후 Entry 2+Exit 2의 작은 Joint refinement는 허용
- 목적함수에 Raw 총수익률만 사용하지 않음

권장 목적함수는 다음 제약을 통과한 뒤에만 비교한다.

```text
거래 수 하한
+ 평균수익률 양수
+ MDD 상한
+ Fold 간 부호 일관성
+ Negative control 대비 우위
→ 제약 통과 후보끼리 보수적 utility 비교
```

### 11A.6 유전알고리즘 활용

유전알고리즘은 탐색 공간이 큰 상태전이 절 조합의 브레인스토밍 도구로만 사용한다.

허용:

- 한 Band·한 Family 내부
- 상태전이 순서 불변
- Inner discovery fold
- Population 16~32·최대 8~12세대
- 전체 평가 개체 최대 256
- 구조 중복 제거 후 후보 제안

금지:

- 시총 Band를 유전자화
- Family 간 교배
- Outer fold fitness 사용
- GA 우승자를 최종 후보로 직접 승격
- GA·조건최적화·TPE를 연속 실행하면서 Trial 수를 숨김

GA가 생성한 모든 개체·세대·평가 횟수는 multiplicity ledger에 포함한다. 이후 QMC/Optuna 후보와 같은 Selection·FDR·Outer fold 기준을 적용한다.

### 11A.7 Rolling Walk-Forward 활용

`RollingWalkForwardTest`는 Native 도구 중 최종 확인에 가장 가치가 크다. 기존 DB만 사용하므로 결과 명칭은 `rolling development`이며 OOS로 부르지 않는다.

| 구간 | 역할 |
|---|---|
| Train | Native 조건·변수 최적화 |
| Valid | 조기 중지·후보 선택 |
| Test | 동일 rolling cycle 내 development 확인 |
| Final outer folds | Native 최적화와 분리된 프로그램 판정 |

필수 receipt:

- Window별 Train/Valid/Test 날짜
- 사용 가능한 실제 거래일 수
- 각 Window source hash·variables
- Optimizer sampler·seed·trial 수
- 선택되지 않은 Trial 포함 전체 결과
- Window 간 변수 drift
- Test 부호·MDD·거래 수

Rolling 결과가 좋아도 최종 outer folds를 대체하지 않는다.

### 11A.8 Native 도구 Funnel

```text
시총 Census
→ BackFinder event snapshot
→ 상태전이 발생량 Gate
→ Negative controls
→ QMC raw 후보
→ OptimizeConditions 절 선택
→ 공식엔진 Selection screen
→ Rolling Walk-Forward development
→ Family×Band Outer folds
→ 적격 Cell만 Entry Optimize
→ Entry 동결 후 Exit Optimize
→ Entry 2+Exit 2 Joint local refinement
→ 봉인 확인구간 단 1회
→ 종료
```

마지막 줄의 의미는 BO 결과를 본 뒤 동일 Outer folds를 반복 접촉하지 않는다는 것이다. BO는 Inner/rolling 범위에서만 수행하고, 사전 봉인된 확인 구간을 단 한 번 평가한다.

| N0-7 Multiplicity | 모든 Native trial 통합 집계 | 경제 판정 금지 |

### 11A.11 24~48시간 Compute Budget

장시간 실행은 허용하되 시간만 오래 쓰는 것을 성실한 탐색으로 간주하지 않는다. 모든 단계는 평가 수·유효 후보 수·중지 이유를 함께 관리한다.

| 단계 | 최대 Active 변수 | 평가 Budget | 시간 배분 상한 | 산출물 |
|---|---:|---:|---:|---|
| Resource benchmark | — | 대표 6 jobs | 1시간 | Serial/2-way throughput·memory |
| BackFinder/Census | 파생축 10~20 | Band×Family event scan | 3시간 | Event·분위수·희소성 |
| 조건절 탐색 | 후보절 10, 활성 5 | exact 최대 64 또는 GA 256 | 5시간 | Clause lineage |
| Entry QMC/TPE | 6~8 | 56~88/Cell | 10시간 | Entry trials |
| Exit QMC/TPE | 4~6 | 40~64/Cell | 8시간 | Exit trials |
| Joint local | 4 | 16~24/Cell | 4시간 | Entry×Exit local trials |
| Rolling development | 완성 10~14 | Top 2~4 pairs | 10시간 | Window stability |
| 봉인 확인 | 완성 10~14 | Pair별 outer 1회 | 4시간 | 최종 development verdict |
| 여유·재시도 | — | Error budget 내 | 3시간 | Recovery receipt |

총 목표는 24~36시간이며 hard stop은 48시간이다. 여러 적격 Cell이 있으면 사전등록된 우선순위 상위 2개까지만 이 Budget으로 탐색한다. 나머지는 다음 독립 Batch로 넘긴다.

표의 Trial 수는 상한이며 Benchmark 결과로 축소한다. 실제 허용 평가 수는 다음으로 산출한다.

```text
E_cap = floor((48시간 - Census/검증/복구 예약시간) / 대표 평가 p95 시간)
```

- Census·BackFinder 예약: 3시간
- Rolling·봉인 확인 예약: 14시간
- 복구·오류 Budget: 3시간
- 탐색 가용시간: 최대 28시간

Entry/Exit/Joint/Random 평가 수의 합이 `E_cap`을 넘으면 QMC/TPE Budget을 비례 축소한다. 성공 결과를 본 뒤 hard stop이나 E_cap을 늘리지 않는다.

### 11A.12 Resource·Resume 계약

과거 공식엔진 4-way 병렬 실행에서 심각한 경합이 있었으므로 병렬도를 미리 고정하지 않는다.

1. 대표 Job 6개를 Serial과 2-way로 각각 Benchmark한다.
2. 2-way가 처리량 1.5배 이상이고 peak memory 70% 미만일 때만 concurrency 2를 허용한다.
3. 그 외에는 Serial로 실행한다.
4. Concurrency 4 이상은 사용하지 않는다.
5. Trial마다 `receipt.json`과 Native DB를 commit checkpoint한다.
6. Resume는 완료 Trial hash를 재사용하고 같은 Trial을 재실행하지 않는다.
7. Engine timeout, runner timeout, monitor timeout, recovered terminal을 분리한다.

### 11A.13 매수·매도 단계별 최적화

| 단계 | 고정 | 최적화 | 다음 단계 진입 |
|---|---|---|---|
| B0 Entry 구조 | 시총 Band·Family·기준 Exit | Entry 6~8변수 | Control·Inner gate |
| S0 Exit | Top Entry source | Exit 4~6변수 | Rolling gate |
| BS0 Joint local | 나머지 Entry/Exit 변수 | 민감도 상위 Entry 2 + Exit 2 | 봉인 확인 |

기준 Exit 하나 때문에 좋은 Entry를 놓치는 것을 막기 위해 Entry 단계에서는 baseline Exit와 최소 1개 단순 시간 Exit를 별도 Arm으로 평가한다. 그러나 Entry 후보마다 모든 Exit 조합을 전수평가하지 않는다.

Exit 단계에서는 Top Entry 최대 3개만 사용한다. Entry와 Exit를 바꿔가며 반복하는 coordinate cycle은 1회만 허용한다. 두 번째 cycle은 Outer 결과를 간접적으로 학습할 위험이 있으므로 금지한다.

### 11A.14 봉인 확인구간

Native Rolling의 Test와 프로그램 최종 확인구간을 분리한다.

| 구간 | 사용 |
|---|---|
| `DEV_DISCOVERY` | BackFinder·QMC·조건/GA 탐색 |
| `DEV_ROLLING` | Native Train/Valid/Test rolling |
| `DEV_HOLDBACK` | 프로그램 최종 확인, Pair별 단 1회 |

`DEV_HOLDBACK`은 C0 Census 이후 성과를 읽기 전에 달력·Band 표본 수만으로 봉인한다. D1/D2/Paired에 사용된 구간과 중복 여부를 Manifest에 기록하고, 가능한 범위에서 Native discovery/rolling과 날짜가 겹치지 않게 한다. 기존 DB이므로 결과는 여전히 development이며 OOS로 부르지 않는다.

### 11A.15 도구 선택 규칙

| 상황 | 사용할 도구 | 사용하지 않을 도구 |
|---|---|---|
| Event·분포·시총 표본 | BackFinder | Optuna·GA |
| 조건 후보 조합 <=64 | OptimizeConditions exact | GA |
| 조건 후보 조합 65~1024 | GA capped | BruteForce |
| 숫자 변수 초기 피복 | QMCSampler | TPE 단독 시작 |
| 숫자 변수 국소 개선 | TPESampler | CMA-ES 기본 사용 |
| 변수·성과 시기 안정성 | RollingWalkForwardTest | 단일 전체기간 최적화 |
| 최종 경제 판정 | 프로그램 Outer folds | Native best score 단독 |

OptimizeConditions와 GA는 같은 Cell에서 기본적으로 둘 다 실행하지 않는다. 조합 수에 따라 하나를 선택한다. Native 도구를 많이 쌓는 것이 아니라 서로 중복되는 도구를 선택적으로 사용한다.
