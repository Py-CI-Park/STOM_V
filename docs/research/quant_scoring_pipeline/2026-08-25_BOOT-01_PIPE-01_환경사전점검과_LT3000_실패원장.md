## 4. 원인별 깊은 검토

### 4.1 “no-trades”는 왜 실패를 숨겼는가

두 FAILED_BREAKOUT_RETURN 작업에는 다음 직접 증거가 함께 존재한다.

1. 실제 데이터 배열을 읽고 전략에 진입했다.
2. `BackEngine:0=engine_strategy_exception`이 기록됐다.
3. 종목 `006740`의 구체적인 tick index에서 동일한 TypeError가 발생했다.
4. 그런데 metrics가 없다는 일반 CLI 메시지를 job finalizer가 정상 무거래로 받아들였다.

`backtest_jobs.py`의 `_is_no_trades()`가 일반 “without metrics” 메시지를 신뢰하고, finalizer가 diagnostics의 전략 예외보다 `no_trades`를 우선한 경로가 상태 모순과 일치한다. 다음 SYS-01에서는 **실행 예외가 존재하면 no-trades를 만들 수 없다는 불변식**을 validator로 고정해야 한다.

코드에서 `trade/base_strategy.py`의 `self.high_low[self.code][1]` 접근과 `backtest/backengine_base.py`의 `self.high_low = []` 초기화가 예외 메시지와 강하게 부합한다. 다만 원본 traceback과 red/green 재현을 이번 단계에서 만들지 않았으므로, 정확한 root를 확정 사실로 승격하지 않는다. 확정 범위는 `TYPE_ERROR_LIST_STRING_INDEX`까지다.

### 4.2 data-response timeout 4건

네 건은 모두 같은 경계를 보인다.

| 관측 | 값 |
|---|---|
| expected response | 1 |
| received response | 0 |
| missing response | 1 |
| wait | 150초 |
| engine process | alive |
| strategy event | 0 |

이는 “조건식이 나빠서 거래하지 않았다”도, “전략 표현식이 예외를 냈다”도 아니다. 엔진이 데이터 요청에 응답하지 못한 경계 실패다. 내부 원인은 `NOT_OBSERVED`이며, strategy source를 바꾸지 않고 data-load/worker identity/heartbeat를 계측해야 한다.

### 4.3 watchdog timeout 2건

두 작업은 manager queue에 오래 기다린 것이 아니다. 제출 후 0.023초 이내 시작했고, 210초 경계에서 watchdog이 회수됐다. 이후 같은 worker는 바로 다음 작업을 시작해 완주했으므로 지속적인 manager queue deadlock도 반박된다.

그러나 로그가 0 bytes이고 process diagnostics가 없어 계산량 과다, child deadlock, data load 정지 중 무엇인지 판단할 수 없다. 따라서 “timeout을 300초로 늘리면 해결”도 “조건식을 단순화하면 해결”도 현재는 근거가 없다.

### 4.4 성공 2건의 경제적 의미

| 후보 | 거래수 | 평균 수익률 | 총수익률 | MDD | 경제 판정 |
|---|---:|---:|---:|---:|---|
| ABSORPTION_REVERSAL `cb7275dfee` | 2 | -1.67% | -1.67% | 1.03 | `INCONCLUSIVE` — 관측은 음수 |
| COMPRESSION_CONFIRMED_BREAKOUT `f6320dda9d` | 4 | -0.48% | -1.93% | 4.01 | `INCONCLUSIVE` — 관측은 음수 |

두 건은 “프로세스가 끝났다”는 실행 성공일 뿐이다. 거래수가 너무 적고 둘 다 손실이므로 조건식 자율 개선의 성공, 수익성 성공, robust 후보, 승격 후보라고 부를 수 없다.

## 6. 재시도·교정 정책

| failure type | 지금 바로 동일 재실행 | 먼저 해야 할 일 | 허용되는 첫 재현 |
|---|---:|---|---|
| masked strategy exception | 금지 | status precedence 회귀 테스트 + runtime parity 원인 교정 | 동일 prereg/source identity를 유지한 red/green 재현 |
| engine data-response timeout | 금지 | request/worker/data-load heartbeat와 engine identity 기록 | 계측된 동일 후보 격리 1회 |
| watchdog no telemetry | 금지 | child PID·CPU·RSS·phase checkpoint·last-progress 기록 | 후보별 격리 1회 |
| underpowered negative success | 확대 금지 | SYS-01이 실행 성공과 경제 성공을 분리하는지 검증 | RES-01 사전등록 이후에만 |

다음은 “교정”이 아니라 결과 후 규칙 변경이므로 금지한다.

- timeout을 근거 없이 210초에서 더 크게 올리기
- 손실 후보의 threshold·시간창·Band 경계를 결과를 보고 미세조정하기
- 실패한 행을 분모에서 빼고 성공률을 다시 계산하기
- `no_trades`를 정상 실행으로 간주해 checkpoint 재개 시 재사용하기
- 원본 Evidence JSON을 새 상태로 덮어쓰기
