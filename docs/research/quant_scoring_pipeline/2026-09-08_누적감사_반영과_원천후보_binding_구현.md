## 4. 실제 구현한 연결

```text
준비계약 + trusted metadata 파일/expected hash
       ↓
기존 validate_sealed_candidates
       ↓ source·seed·canonical·window·후보 universe 대조
등록 후보 하나
       +
읽기 전용 SQLite의 지정 종목/하루
       ↓ full hash·size·sidefile·table·row·cell·VM budget
검증된 TickDay + SliceReceipt
       ↓ 기존 build_event_stream / triggered_positions
BoundEventStream (NO_EXECUTION_GRANT)
```

- res04_input_binding.py: CandidateFiles, load_candidate, build_bound_event_stream. 기존 RES01/RES02 검증 owner를 그대로 재사용한다. 임의 source text를 exec/eval하거나 새 전략을 실행하지 않는다.
- res04_tick_source.py: SourceRequest, read_tick_slice. 기존 SQLite readonly/fingerprint와 54열 tick projection/normalizer 재사용. 결측/비유한 원시 행은 legacy zero-fill 전에 거부한다.
- 운영 DB와 카탈로그의 테이블을 추가하지 않는다. 이번 실행은 격리된 합성 SQLite 및 기존 봉인 문서 메타데이터에 한정했다.
- 이 코드는 호출자 권한을 발급하는 서비스가 아니다. 실제 시장자료에 호출하는 Stage F/연구 허가는 별도이며 API/runner에 자동 연결하지 않았다.

## 5. 데이터/자원 보호

| 경계 | 구현 |
|---|---|
| 범위 | 요청 날짜가 준비계약 Fold 밖이면 파일 open 전 거부 |
| 파일 | 로컬 절대경로, full SHA와 size, 최대32GiB |
| sidefiles | -wal/-shm/-journal 존재 시 immutable read 중지 |
| 읽기 | 기존 mode=ro/immutable=1/query_only 연결 |
| 테이블 | six-digit ASCII symbol, 실제 table만; view 거부 |
| 쿼리 | parameterized 시간·LIMIT, owner의 quoted column identifiers |
| 행 | 기본3000/최대10000, 초과분을 부분 성공으로 내보내지 않음 |
| 값 크기 | SQLite SQLITE_LIMIT_LENGTH=16384, fetch 전에 적용 |
| 값 의미 | 행마다 즉시 strict numeric/finite 검증 후 보관 |
| 계산 | SQL VM progress budget; 기존 event factor work cap 유지 |
| 변경 감지 | 읽기 전/후 full fingerprint 비교, sidefile 재확인 |

immutable=1은 OS 파일을 물리적으로 동결하지 않는다. 안정된 source snapshot이라는 전제를 여전히 요구하며, hash는 승인 서명이나 적대적 동시 변경 방지 잠금이 아니다. trusted caller의 expected hash가 기준이다.
full DB hash를 매 slice 전후 계산하므로 큰 DB에서 비싸다. 현재는 correctness 경로다. 실제 대량 실행 전에는 기존 artifact/snapshot owner 아래 검증된 snapshot 수명 단위로 비용을 분산하고 동등성·drift 방어를 시험해야 한다. 이 개선 없이 고성능 production 준비 완료로 보고하지 않는다.
