# QSP7 tick/min 이중 레인 파이프라인 실측 검증과 연구 실행 계획

> 작성일: 2026-08-03
> 브랜치: `feature/qsp7-platform-completion-20260803`
> 상위 문서: [2026-08-03_qsp7_platform_completion_roadmap.md](./2026-08-03_qsp7_platform_completion_roadmap.md) (P0~P6 로드맵)
> 문서 역할: **"back DB → 백테스트 → 분석 → 조건식 생성 → 공식 검증"** 파이프라인이 실제로 성립하는지 **당일 실측으로 증명**하고, tick/min을 **각각 독립 운영**하는 이중 레인 설계와 연구 목표·KPI를 확정한다
> 안전 경계: 운영 DB 쓰기, 실거래 반영, 전체청산 이후 시세 사용, OOS 재학습, 후보 자동 채택 금지

## 0. 🧭 1분 요약

| 질문 | 답 |
|---|---|
| 파이프라인이 실제로 성립하나? | **예. 오늘(2026-08-03) 양 레인 모두 끝까지 관통 실증했다** — back DB → 엔진 백테스트 → 공식 CSV(54열) → QSP7 경로 분석(제외 0건) |
| tick과 min을 각각 운영할 수 있나? | 데이터·엔진·분석은 **이미 가능**. 남은 것은 ① 레인별 기준선 manifest ② 레인 인식 UI ③ **생성 엔진의 구조 어댑터** |
| 오늘 발견한 최대 장애물은? | 기존 생성 엔진(`revision/`)이 **HIER 구조 매수식만 파싱**한다. tick 기준선은 평탄한 5절 필터라서 **파싱 거부**("no cap leaves") — 구조 어댑터 없이는 tick 레인에서 자동 생성이 불가능 |
| min 레인의 제약은? | min 기준선은 HIER 파싱 OK지만 **리프가 1개** → 리프 제거(surgeon)는 쓸 게 없고 **필터 추가(filtersmith)가 주력 액션** |
| 설계구간 백테스트는 감당 가능한가? | **예.** 실측 환산: min 213일 ≈ 엔진 8개로 **약 16분**, tick 952일 ≈ **약 2시간**. 하루에 후보 여러 개 시험 가능 |
| 이 문서로 무엇이 바뀌나? | 로드맵에 **P2-8(구조 어댑터) · P1 레인 콘솔 · P6 레인별 manifest**가 추가되고, 연구 KPI가 수치로 고정된다 |
| 매수 파생 변수 확장은? | **채택 (§10).** 엔진 캡처가 이름 추가만으로 확장되는 구조이고, 파생 18항 미러 재계산기가 이미 존재 — 3루트(사후 파생 → DB 재구성 → 엔진 캡처)로 단계 도입, STOM-표현가능성이 지배 필터 |

핵심 한 문장:

> **파이프라인의 모든 배관은 오늘 물이 흐르는 것까지 확인했다. 막힌 곳은 단 하나 — 생성 엔진이 tick의 평탄한 조건식을 읽지 못한다. 그래서 P2의 첫 작업은 "구조 어댑터"다.**

## 2. 🚧 오늘 발견한 이중 레인의 실제 장애물

### 2.1 생성 엔진의 구조 가정 vs 실제 기준선 (실측)

| 기준선 | 구조 | `parse_leaves` 결과 | 영향 |
|---|---|---|---|
| min `Min_B_Study_251227` (80줄) | HIER — 시분초<120000 → 시가총액<100000 | **ok=True · 리프 1개** | 파싱은 되나 리프 1개 → **surgeon(리프 제거)은 무용, filtersmith(필터 추가)가 주력** |
| tick `ResearchTest_Tick_B_...` (17줄) | **평탄한 elif 5절** (계층 없음) | **ok=False · "no cap leaves (시가총액)"** | **생성 엔진 전면 불가** — 어댑터 필수 |

### 2.2 이것이 의미하는 것

> **비유:** 자동 재단기(생성 엔진)는 "상의/하의 구분이 있는 옷본(HIER)"만 읽도록 만들어졌다. min 옷본은 구분이 있어서 읽히지만 조각이 1개뿐이고, tick 옷본은 구분 자체가 없어서 기계가 뱉어낸다. **기계를 버릴 게 아니라, 평탄한 옷본도 "조각 1개짜리"로 읽게 어댑터를 끼우면 된다.**

| 레인 | 쓸 수 있는 자동 액션 (어댑터 후) |
|---|---|
| min | **add_filter**(필터 추가) 중심 + 매도식 데이터 구동 생성(P2) |
| tick | 어댑터 후 add_filter + 매도식 생성. 장기적으로 tick 기준선의 HIER화(시간밴드×시총단계 재구성)는 **별도 연구 결정** |

### 2.3 로드맵에 추가되는 작업 (상위 문서 P0~P6에 병합)

| 신규 항목 | 단계 | 내용 |
|---|---|---|
| **P2-8 구조 어댑터** | P2 선두 | `hier_ast`에 평탄 elif 체인을 "단일 리프 + 절 목록"으로 읽는 경로 추가 → tick/min·매수/매도 4조합 모두 파싱 가능하게 |
| **P1-6 레인 콘솔** | P1 | 워크벤치 상단에 **레인 선택(tick/min)** — 선택 즉시 기준선·기간·전체청산·후보 family가 그 레인 것으로 고정 |
| **P6-4 레인별 manifest** | P6 | tick/min 각각 `lane_manifest_{tick,min}.md`: 기준선 buy/sell 이름·해시, 설계/OOS 기간, 세션 경계, 비용 |
| **P0-8 tick 신규 control** | P0 직후 | 37열 legacy tick control을 **54열 modern으로 재발급** (설계·표본밖 구간 각 1회, 약 2시간) |

## 4. 🎯 연구 목표와 KPI

### 4.1 최종 목표 (변경 없음)

> 레인별로 **설계구간과 비중첩 OOS에서 모두 손익이 개선**되는, 사람이 읽을 수 있는 조건식을 만들어 사람 승인으로 채택한다.

### 4.2 단계별 KPI (측정 가능한 수치로 고정)

| 단계 | KPI | 현재 | 타겟 |
|---|---|---:|---:|
| 플랫폼 | 후보→OOS 판정 조작 수 | 수동 7단계 | **3클릭** |
| 플랫폼 | 서버 재시작 후 분석 복원 | 0% | **100%** |
| 플랫폼 | 하드코딩 임계값 | 9개 | **0개** |
| 플랫폼 | 구조 어댑터 파싱 성공 | 2/4 조합 | **4/4** (tick·min × buy·sell) |
| 연구(min) | 설계 pair 실행 후보 수 | 0 | **라운드당 4~8개** |
| 연구(min) | 설계 개선 후보 | 0 | **≥1개** (비용 후 손익·MDD·거래수 동시 확인) |
| 연구(min) | OOS 동시 개선 | 0 | **≥1개** |
| 연구(tick) | modern 54열 control 재발급 | 0/2 | **2/2** (설계·표본밖) |
| 연구(tick) | 비용 후 건당 손익 | −6,079원 | **개선 방향 확인** (구체 수치는 설계 pair 후 설정) |
| 공통 | 가상↔공식 오차 표 | 없음 | **후보 5개 이상 축적** |

### 4.3 연구 회전 목표 (실측 시간 기반)

| 항목 | 목표 |
|---|---|
| min 후보 1개: 생성→설계 pair→판정 | **1시간 이내** (백테 13분 + 분석·검토) |
| min 1라운드(후보 4~8개) | **반나절** |
| tick 후보 1개 | **한나절** (백테 60분 × 2구간) |
| 라운드 종료 판정 | `convergence` 규칙 — 3라운드 연속 무개선 시 축 변경 |

### 4.4 성공/실패의 정직한 정의

| 결과 | 해석 |
|---|---|
| 설계 개선 + OOS 개선 | 채택 후보. 사람 승인 대기 |
| 설계 개선 + OOS 악화 | **과최적 증거로 원장에 보존** — 실패가 아니라 지식 |
| 후보 0개 생성 | 근거 부족 — 정상 동작. cohort를 바꿔 재시도 |
| 전 라운드 무개선 | "이 기준선·이 축으로는 안 된다"는 **결론** — 축 변경(매수/시간대/레인) |
