# RES-04P 최종 사전등록 정의: E1 우선·R1 기술통계

작성일: 2026-09-08. 권위: 사용자의 연구 설계·개발 결정 위임에 따른 정의 문서.
이 문서는 실제 연구 실행, 경제 G0/G2, Holdout, 자동채택, 운영 DB write를 승인하지 않는다.
최종 검토 판정과 정의 SHA-256은 별도 TASK_RECEIPT에 기록한다. 원문·과거 결과는 변경하지 않는다.

## 1. 무엇을 확정했는가

| 항목 | 확정 내용 | 의미하지 않는 것 |
|---|---|---|
| E1 주 가설 | 지속 true의 반복 틱이 아니라 관측 false 이후 true 전환을 사건으로 분리 | 수익성 개선의 확인 |
| R1 보조 진단 | 같은 시점의 5 Family 동시 발화·단독 발화·비발화 집계 | 매매 논리 충돌 확정, router의 효과 |
| 후보 | preparation의 기존 7개 ID·원문 manifest 정의 고정 | PnL을 보고 후보 재선택 |
| 입력 | previously-exposed 개발 원천의 실제 full hash·4개 개발 fold 고정 | 독립 확인 자료, Holdout |
| 표본 기준 | 총 onset 200, fold별 20, onset 발생일 20, 종목 10 | 검정력 또는 경제적 유의성 보장 |
| 실행 | 현 작업에서 0건 | Stage F 승인 |

## 2. 기존 초안에 대한 명시적 설계 정정

1. 과거 `2026-08-26_res02_event_gate.json`은 사건 행이 아니라 집계·선정 metadata다. 이를 사건 입력인 것처럼 재사용하지 않는다. 해당 파일의 해시는 선정 이력으로 유지하고, 실제 관측은 고정한 raw source와 후보 manifest 및 구현 identity로 재구성한다.
2. 기존 E1/R1 이중 가설 초안을 좁혀 **E1 primary / R1 descriptive only**로 확정한다. E1 표본이 부족할 때 R1으로 대체 통과시키지 않는다. R1의 독립 적격성 threshold와 router 선택은 이번 정의에 없다.
3. 입력 hash와 미래 출력 hash를 구분한다. 아직 실행하지 않은 event output/inventory의 hash는 생성하지 않는다. 해당 hash는 향후 실제 실행에서 산출·대조할 값이며 현재 정의 완료를 위해 임의 값으로 채우지 않는다.
4. 현재 구현 identity는 기준 commit과 16개 source Git blob 및 runtime 버전으로 고정한다. 상세 값은 definition JSON과 receipt schema에 동일하게 포함된다. 이후 변경 시 새 정의·새 검토가 필요하다.

`preparation_sha256` 모델 필드는 모델 정규 JSON의 해시다. 위 raw 파일 bytes hash와 서로 다른 namespace다.
원천 경로·4개 날짜 구간·7개 ID는 준비 JSON에 열거되어 있다. DB는 읽기 전후 full hash 및 sidefile 부재를 재검사한다.

예정 inventory는 각 moneytop 행을 KST HHMMSS >=090030, <093000으로 먼저 제한한 뒤 unique symbol/day와 7개 후보를 전개한다. 기간 전체 moneytop 목록을 해당 시간대의 구성으로 오인하지 않는다. 빠진 table/day/행은 예상 inventory에서 삭제하지 않고 결측 사유로 남긴다. 준비된 `assess_candidate`는 선언된 inventory에 대한 완결성만 검사하므로 **원천 universe를 고정하는 orchestration은 실제 Stage F 전에 별도 구현·검증**해야 한다.

## 4. 사건·대조군·겹침

- 기존 recorded-row factor와 실제 `triggered_positions`를 재사용한다. warmup은 max(60, 2 × 각 window); 마지막 source tick은 제외한다. 이력의 시간 기반 의미를 새로 만들지 않는다.
- onset = triggered true AND previous_triggered false. 첫 관측·1초 초과 gap 직후 predecessor는 unknown이며 false로 대체하지 않는다. false 관측은 reset 정보로 유지한다.
- 같은 candidate/family/fold/day/symbol의 known-predecessor true pool에서 onset 개수만큼 SHA-256 순위로 비복원 선택한다. 순위 문자열·seed·tie-break는 definition JSON에 고정한다. onset과 control의 겹침은 허용한다.
- 대조군은 전체 stratum을 보고 고르는 **회고적 진단**이다. 온라인 진입 정책·무작위 실험·보정된 p-value·인과 효과 추정으로 해석하지 않는다.
- R1은 동일 원천 projection 및 stratum의 7개 후보를 요구한다. 공통 관측 timestamp 교집합에서 Family 내부 OR 후 쌍별 co_firing/a_only/b_only/neither를 계산한다. 교집합 제외 수를 별도 표시한다. 결측 후보는 0 겹침이 아니다.

## 5. 정상 중지와 프로그램 판정 우선순위

```text
자원 한도 초과             -> RESOURCE_LIMIT
입력 불일치·실행 오류       -> ERROR
누락·평가 불가 하나라도 있음 -> BLOCKED_DATA
7후보 모두 완전·표본 미달    -> NORMAL_STOP (G0 없음)
그 외 표본 충족 후보 있음    -> REVIEW_ONLY (별도 검토만 가능)
```

후보의 INCOMPLETE/NOT_EVALUABLE은 전체 표본 수를 null로 남긴다. 실제 0 onset과 구분한다. 후보별 다른 definition hash를 섞어 표본 하한을 넘길 수 없다. R1은 위 STOP을 구제하는 fallback이 아니다.

## 6. 예상 영수증·의미 검증

정확한 Draft 2020-12 schema: `planning/2026-09-08_res04p_expected_receipt.schema.json`.
SHA-256: `4197de7a350b75c444c34657e6ad5efc799cee8810aaafaed50ad2204d5e29f1`.

schema는 7개 후보·4fold·typed status·입력/출력 identity·source/overlap manifest refs·coverage/errors·자원/정지 사유를 정의한다. 추가 PnL 등 필드는 허용하지 않는다. 구조 시험의 dummy hash는 테스트 메모리에만 존재하며 실제 Stage F receipt가 아니다.

JSON Schema 통과만으로 실행 영수증이 유효해지지 않는다. 향후 supervisor는 다음 의미 검사를 수행해야 한다.

1. 참조 artifact 존재·bytes SHA 및 실제 bound stream에서의 재생성 대조.
2. source-bound inventory 해시, 예상/수신/누락 목록의 정확한 일치 및 중복 없음.
3. 후보 합계·fold 합계·날짜/종목 수·scope 수의 원본 집계 대조.
4. 7후보 정의 해시와 준비/선정 manifest 일치, R1 각 보고서의 완결성 확인.
5. 프로그램 판정 우선순위·stop reason 일치. 해시는 서명/사용자 승인이나 신뢰 가능한 출처 증명이 아니다.
6. 실행 환경/구현 identity, 감독 프로세스 deadline과 자원 측정 검증.

## 7. 예산과 다음 허용 행동

현재 연구 job 권한 0. 향후 Stage F 한도 1 worker/1,800초. 기존 후속 경제 job 상한 40은 승인으로 해석하지 않는다. 요청 10,000 rows, SQLite value 16,384 bytes, factor cells 2,000,000, 후보 scopes 20,000/observations 5,000,000, overlap observations 200,000. 초과 시 부분 성공 없이 RESOURCE_LIMIT.

계획 Gate의 산출물은 정의·manifest·금지 목록·정확한 receipt schema·구현 identity·독립 검토다. 실제 원천 census, event output, 감독 실행 및 연구 승인은 이후 Stage F의 선행 조건이다. 이를 혼동해 계획을 무기한 미완료로 남기거나, 반대로 계획 완료로 실제 연구를 실행하지 않는다.

검토 승인 후 개발 순서: SYS-05 → ANA-05 → ANA-06 → ANA-07 → ANA-08 → UX-06. 기존 CardV3/Bundle/TradeArtifactContract/TradePath/Catalog/Formal Ledger/ContextPack/ChartFrame를 재사용하고 페이지 기능을 단계별 연결한다. 운영·경제 검증은 별도다.
