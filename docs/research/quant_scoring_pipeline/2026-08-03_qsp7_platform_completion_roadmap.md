## 1. 🎯 이 시스템은 무엇이고 왜 만드는가

### 1.1 비유

> **축구 경기 다시보기(VAR) 분석실**을 만들고 있다.

| 비유 | 실제 |
|---|---|
| 끝난 경기 녹화본 | 공식 백테스트 결과 CSV (매매 기록 전체) |
| 경기장 전체 카메라 | tick/min 시세 DB (초 단위 · 분 단위) |
| "여기서 다르게 했으면?" 시뮬레이션 | 가상 매도 재생 (같은 진입 고정) |
| 감독의 최종 판정 | **공식 백테스트 엔진** (유일한 정본 권위) |
| 코치진 승인 | 사람이 후보 선택·승인 |

AI는 정답을 선포하지 않는다. **증거를 정리하고 가설을 만들 뿐**이고, 채택은 공식 엔진과 사람이 정한다.

## 2. 📐 데이터 실측 — tick과 min은 다른 세계다

### 2.1 실제로 가진 데이터 (2026-08-03 DB 직접 조회)

| 항목 | **tick (1초 스냅샷)** | **min (1분봉)** |
|---|---|---|
| 데이터 기간 | 2022-03-23 ~ 2026-02-27 (**약 4년**) | 2025-04-07 ~ 2026-02-27 (**약 11개월**) |
| 하루 중 시간대 | **09:00:00 ~ 09:30:00 (30분)** | 09:00 ~ 15:19 (전 시간) |
| 일별 DB 파일 | `stock_tick_YYYYMMDD.db` 다수 | `stock_min_YYYYMMDD.db` (2025-04-07~) |
| 통합 DB | `stock_tick_back.db` (29.7GB) | `stock_min_back.db` (1.45GB, 2025-04-07~) |
| 만들 수 있는 전략 | **장 시작 30분 전용 초단타** | 하루 종일 쓰는 전략 |
| 제약 | 기간은 길지만 하루가 짧다 | 하루는 길지만 **기간이 짧다** |

> **비유:** tick은 "4년치 아침 뉴스만 녹화한 테이프", min은 "11개월치 하루 종일 녹화한 테이프". 같은 방법으로 다룰 수 없고, 조건식 문법·함수·후보군도 분리해야 한다.

### 2.2 tick — 설계/표본밖 구간 확정 (QSP2ANCH_R8C2_B 기준)

| 구간 | 기간 | 거래 수 | 비용 전 건당 | 비용 후 건당 | 평균 비용 | 판정 |
|---|---|---:|---:|---:|---:|---|
| 설계 | 2022-04-01 ~ 2024-03-31 (2년) | 13,718 | **+4,411원** | **−6,079원** | 10,490원 (0.210%) | 비용 때문에 적자 전환 |
| 표본 밖 | 2024-04-01 ~ 2026-02-27 (23개월) | 10,755 | −1,396원 | **−11,875원** | 10,480원 | 비용 전에도 적자 |

경로 연구용 tick control은 별개다: `20260727_112426_...` = 2025-04-07~2025-04-30(18일), 4,450건.

### 2.3 min — 구간 미정이고 **OOS로 남겨둔 구간이 없다**

| 항목 | 값 |
|---|---|
| 현재 control | `20260802_063342_MinBStudy251227_22848` = 2025-04-07~2026-02-27, **6,659건 (211일)** |
| 문제 | min 데이터 **전 기간(11개월)을 control 하나에 다 써버렸다** |
| 결과 | 설계 시험을 치면 **"한 번도 안 본 기간"이 0개** → OOS 관문 통과 불가 |

**분할안 (P6에서 확정)**

| 안 | 설계 구간 | OOS 구간 | 장단점 |
|---|---|---|---|
| **A (권장)** | 2025-04-07 ~ 2025-11-28 (약 8개월) | 2025-12-01 ~ 2026-02-27 (약 3개월) | 설계 표본 확보, OOS는 짧음 |
| B | 2025-04-07 ~ 2025-09-30 (6개월) | 2025-10-01 ~ 2026-02-27 (5개월) | OOS 신뢰↑, 설계 표본↓ |

> min은 데이터가 더 쌓이기 전까지 **OOS가 짧을 수밖에 없다.** 이건 코드로 못 고치는 구조적 한계이며 `limitation_ledger.md`에 고정해야 한다.

## 5. 🧠 핵심 진단 — 분석은 강하고 생성은 약하다

### 5.1 매수 생성 엔진 vs 매도 생성기

| 항목 | 매수 (`revision/*`, 이미 API 노출) | 매도 (`sell_proposer.py`) |
|---|---|---|
| 임계값 출처 | **승 그룹 데이터 분위수** | **코드 상수** (−2, 3.0, 0.65, 1.5, 1.0) |
| 변수 선택 | Cohen's d + **FDR q≤α** | 없음 |
| 후보 생성 조건 | 신뢰 리프(n≥min_n) + 통계 통과 | **해당 거래가 1건이라도 있으면** |
| 후보 다양성 | 서로 다른 리프·변수 축 | 고정 5종 |
| 생성 후 검증 | `intent_gate` 기계 판정 | 문법 체크만 (`self.Sell()` 존재) |
| 반복·수렴 | `round_runner` + `convergence` | 없음 |
| 과최적 방어 | 깊이당 비용 지불(`deep_search`) | 없음 |

> **비유:** 매수 쪽은 "혈액검사 수치를 보고 처방하는 의사", 매도 쪽은 "증상만 있으면 같은 감기약 5종 세트를 주는 자판기".

### 5.2 "인간이 못 하는 분석" 현황

| 능력 | 현재 |
|---|---|
| 수천 건 매매 각각의 매도 후 경로 전수 결합 | 🟢 됨 |
| 매도식 조건절 최초 발동 재생 | 🟢 됨(단일 거래) |
| 매수 31개 변수 승패 판별력 | 🟢 됨(기존 엔진 재사용) |
| **회복한 손실 거래 vs 못 한 거래를 무엇이 가르는가** | 🔴 **없음** — 화면은 회복 여부만 보여줌 |
| 매도 조건 간 상호작용 탐색 | 🔴 없음 |
| 가상↔공식 오차 보정(캘리브레이션) | 🔴 없음 |

**4번이 가장 아깝다.** `leaf_matrix`/`feature_map` 엔진의 라벨만 "이겼나/졌나" → "회복했나/못했나"로 바꾸면 대부분 재사용된다. 가장 싼 큰 개선.
