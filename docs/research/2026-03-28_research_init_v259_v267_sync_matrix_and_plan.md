# 2026-03-28 research/init V2.59~V2.67 공식 업데이트 반영 매트릭스 및 권장 계획

## 문서 목적

이 문서는 `research/init` 브랜치가 부모 계열 브랜치에서 반영한 공식 업데이트를
어떤 관점으로 흡수해야 하는지 정리한 **버전별 매트릭스 + 실행 계획 문서**다.

특히 아래 질문에 답하도록 작성한다.

1. `V2.59 ~ V2.67` 공식 업데이트를 리서치 브랜치에 반영하는 것이 맞는가?
2. 그렇다면 리서치 브랜치 관점에서 어떤 순서와 어떤 방식으로 반영하는 것이 좋았는가?
3. 사용자가 제안한 것처럼 `eeb59864` 이후에 `a9e54002 ~ 44ff7982` 범위를 따라가는 방식이
   실무적으로 타당한가?
4. 실제로는 어떤 내용이 리서치 브랜치에 맞게 흡수되었고, 어떤 문서/호환 보정은 의도적으로 남았는가?

아래의 실무 원칙을 따라야 한다는 것이다.

### 실무 원칙 A / B / C

|---|---|---|
| A | 공식 업데이트 반영 | 부모 브랜치가 반영한 V2.59~V2.67 내용을 리서치 브랜치도 따라가야 함 |

## 왜 `eeb59864` 이후부터 순차 반영이 가장 좋았는가

사용자 의견:

> `eeb59864` 다음부터 `a9e54002 ~ 44ff7982` 범위의 업데이트를 리서치 브랜치에 맞게
> 순차적으로 진행하는 것이 가장 좋았던 것 같다.

이 판단은 타당하다.

### 이유

1. `eeb59864`는 리서치 브랜치에서 배치 런처 종료 원인 확인 개선이 반영된 시점이다.
2. 그 이후 부모 라인에서는 `V2.59`부터 `V2.67`까지 런타임 구조, 홈탭, UI, 백테, tick 전략,
   시장미시구조 분석 등이 단계적으로 누적되었다.
3. 이 누적 변화를 리서치 브랜치가 오래 흡수하지 않으면,
   stale import, 구조 불일치, 설정 키 mismatch, DB 컬럼 mismatch 같은 문제가 쌓인다.
4. 실제로 이번 작업에서도 `webcrawling_homtab` stale 참조, `proc_chqs` 전환,
   `시장미시구조분석` 설정 흐름 등이 그런 누적 미반영의 결과로 확인되었다.

즉, **버전 단위로 순차 흡수했다면 더 작은 충돌로 처리할 수 있었을 가능성이 높다.**

## 버전별로 리서치 브랜치에 어떤 식으로 반영했어야 하는가

### V2.59
- 홈탭 naming (`선물` → `코스피200선물`, `금` → `국제금`)
- `opti_turn` / `opti_kind` 의미 체계 정리
- 가장 먼저 받아야 하는 이유:
  - 이후 홈탭 / 백테 / 전략 설명 문자열이 전부 이 용어 체계 위에 누적되기 때문

### V2.60 ~ V2.63
- UI 다이얼로그, 설정값, style, 홈탭 표현, 백테 조건 표시 정리
- 이 구간은 **UI / 설정 골격 정렬 단계**로 흡수하는 것이 자연스러움

### V2.64 ~ V2.65
- 실질적인 구조 전환 구간
- 웹크롤링 통합, 프로세스 통합, stale split path 제거
- 이건 반드시 **홈탭 → 런타임 → UI consumer** 순서로 세트 반영해야 함

### V2.66 ~ V2.67
- 마감 보강 구간
- 전략/수식/보조 자산 + 시장미시구조 분석 + queue 정리
- 리서치 브랜치 입장에서는 **tick 전략 + microstructure + 설정/DB/UI 경로**를 함께 움직여야 함

### 95285f30 / 44ff7982
- 리서치 브랜치도 최신 기준선에 맞추려면 당연히 포함돼야 했던 실무 fix
