## 3. 핵심 문제점

## 3.1 `STOM_Version_2U` 절차가 `.pyd` 비존재 원칙과 충돌 가능성 높음
**중요도: 높음**

문서는 `STOM_Version_2U`에서 `git merge STOM_Version_2` 후 pyd 변경을 확인하고 추론하는 흐름을 제시한다.

문제는:
- `STOM_Version_2U`는 `.pyd` 파일이 존재하면 안 되는 브랜치인데,
- 문서 절차에는 merge 후 `.pyd`를 어떻게 차단/제거할지 명시적 단계가 없다.

즉,

> **2U 운영의 핵심 제약조건이 절차에 직접 반영되어 있지 않다.**

관련 위치:
- `docs/UPSTREAM_SYNC_STRATEGY.md:368-382`
- `docs/UPSTREAM_SYNC_STRATEGY.md:417-422`

---

## 3.2 `git add -A` 사용은 현재 저장소 운영 규칙과 충돌함
**중요도: 높음**

문서에는 아래와 같은 절차가 있다.

- `git add -A`
- `git add -A && git commit`

하지만 현재 저장소 운영 규칙상 `git add -A`는 금지되어 있다.

문제는:
- 임시 파일
- 로컬 산출물
- 의도치 않은 문서/테스트 변경
까지 함께 스테이징될 위험이 크다는 점이다.

즉,

> **현재 레포 운영 규칙과 직접 충돌하는 실행 예시가 포함되어 있다.**

관련 위치:
- `docs/UPSTREAM_SYNC_STRATEGY.md:295`
- `docs/UPSTREAM_SYNC_STRATEGY.md:334`

참고 규칙:
- `AGENTS.md`의 `git add -A 사용 금지`

## 3.3 `rsync --delete` 절차는 안전장치 설명이 부족함
**중요도: 높음~중간**

문서의 핵심 동기화 절차는 `rsync -av --delete` 기반이다.

이 전략 자체는 강력하지만,
보호 대상이 완전하지 않으면 로컬 커스텀 파일이 삭제될 위험이 있다.

문제는:
- exclude 목록이 충분한지 검증 절차가 없음
- 삭제 전 dry-run 예시가 없음
- 운영자가 어떤 파일이 지워질 수 있는지 미리 확인하는 단계가 없음

즉,

> **전략 자체는 이해되지만, 실행 절차로는 너무 공격적이다.**

관련 위치:
- `docs/UPSTREAM_SYNC_STRATEGY.md:279-292`

## 4. 추가 주의사항

## 4.1 POSIX 도구 전제가 불명확함
**중요도: 중간**

문서는 Windows 경로(`C:\...`)를 사용하면서,
실행 예시는 `tar`, `rsync`, `grep`, `sed` 같은 POSIX 도구를 사용한다.

즉 다음이 불명확하다.
- Git Bash 기준인지
- WSL 기준인지
- 순수 CMD/PowerShell 기준인지

문서 사용자는 실행 환경을 혼동할 수 있다.

관련 위치:
- `docs/UPSTREAM_SYNC_STRATEGY.md:267-299`

## 4.2 export 예시가 바로 실행되기엔 부족함
**중요도: 중간**

예시:


- tar 추출 전 준비 단계가 빠져 있음

즉,

> **예시 명령은 개념 전달에는 충분하지만, 운영 절차 예시로는 불완전하다.**

관련 위치:

## 4.3 pyd 변경 감지 방법이 다소 단순함
**중요도: 중간**

문서에서는 아래 방식으로 pyd 변경 여부를 본다.

```bash
git diff HEAD~1 --name-only | grep '\.pyd$'
```

이 방식은 설명용으로는 이해하기 쉽지만,
merge 방식이나 부모 선택에 따라 의도한 “버전 단위 pyd 변경”만 정확히 잡는 절차라고 보기엔 단순하다.

즉,

> **설명용으로는 괜찮지만 운영 절차 기준으로는 다소 취약하다.**

관련 위치:

- `docs/UPSTREAM_SYNC_STRATEGY.md:374-376`
