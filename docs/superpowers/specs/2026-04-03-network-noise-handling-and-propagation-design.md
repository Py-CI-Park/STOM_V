# STOM_V Network Noise Handling And Propagation Design

## 목적

공식 `STOM_V`에서 외부 네트워크 실패가 발생할 때 `utility/webcrawling.py`와 `utility/telegram_bot.py`가 장문의 traceback을 콘솔에 출력하는 문제를 운영 품질 관점에서 정리한다. 이번 설계의 목표는 외부 사이트 일시 장애를 내부 치명 오류처럼 보이지 않게 바꾸고, 이후 같은 정책을 `2U -> 2U_C -> wt-dev / research` 순으로 전파하는 기준을 만드는 것이다.

## 배경

현재 확인된 런타임 로그는 다음 특성을 가진다.

- 백테스트 자체는 정상 완료된다.
- 완료 이후 홈 데이터 갱신과 텔레그램 polling이 외부 네트워크 예외를 만나면 traceback이 그대로 출력된다.
- 예외 종류는 `ReadTimeout`, `ConnectError`, `NameResolutionError`, `RemoteDisconnected`, `WinError 10065`, `getaddrinfo failed` 등이다.
- 이 예외들은 `api.binance.com`, `finance.naver.com`, 텔레그램 API 같은 외부 서비스 문제이거나 네트워크/DNS 상태 문제일 가능성이 높다.

즉, 이번 이슈는 백테스트 엔진 실패가 아니라 외부 의존성 실패를 “운영 중 흔한 일시 장애”로 다루지 못하는 문제다.

## 범위

1차 공식 수정 범위는 다음 두 파일로 한정한다.

- `utility/webcrawling.py`
- `utility/telegram_bot.py`

전파 범위는 다음 순서를 기준으로 한다.

- `STOM_V`
- `STOM_Version_2U`
- `STOM_Version_2U_C`
- `STOM_V.wt-dev`
- `research/init`

## 비목표

- 부트스트랩 수익률 계산 이상치 수정
- 백테스트/최적화/롤링워크포워드 로직 변경
- 외부 네트워크 자체 복구
- 전체 외부 요청 경로 전면 재설계

## 문제 정의

### 1. webcrawling 문제

`get_korean_stocks`, `get_market_indicator`, `get_crypto_data`는 스레드로 실행되지만 네트워크 예외를 함수 내부에서 정리하지 않는다. 따라서 외부 사이트 응답 지연이나 DNS 문제 발생 시 스레드 traceback이 그대로 남는다.

또한 일부 수집 경로는 실패 시 `thread_join` 처리와 데이터 유지 정책이 명확하지 않아, 홈 데이터 갱신 상태를 해칠 가능성이 있다.

### 2. telegram_bot 문제

텔레그램 polling 초기화 또는 재시작 과정에서 외부 네트워크 실패가 발생하면 라이브러리 traceback이 시스템로그를 오염시킨다. 사용자는 “텔레그램 연결 실패”보다 “프로그램 전체 이상”으로 받아들일 수 있다.

### 3. 운영 품질 문제

현재 구조에서는 외부 네트워크 실패가 아래처럼 보인다.

- traceback 수십~수백 줄 출력
- 정상 완료된 핵심 로그 가림
- 백테스트 실패처럼 오해 유발

운영상 더 적절한 동작은 다음이다.

- 기존 상태 유지
- 짧은 경고만 출력
- 다음 주기에 재시도
- 반복 실패는 과도하게 도배하지 않음

## 접근안 비교

### 1. traceback 유지

- 장점: 개발 중 원인 파악이 가장 쉽다.
- 단점: 운영 환경에서 로그 품질이 가장 나쁘다.
- 단점: 외부 장애를 내부 버그처럼 보이게 만든다.

### 2. 한 줄 경고로 낮추고 이전 데이터 유지

- 장점: 운영 친화적이다.
- 장점: 외부 일시 장애와 내부 치명 오류를 구분할 수 있다.
- 장점: 홈 데이터와 텔레그램 상태를 다음 주기까지 유지할 수 있다.
- 단점: 상세 traceback은 즉시 보이지 않는다.

### 3. 완전 무음 처리

- 장점: 로그가 가장 조용하다.
- 단점: 사용자가 장애를 전혀 인지할 수 없다.
- 단점: 추후 원인 파악이 어려워진다.

## 추천안

추천은 **2. 한 줄 경고로 낮추고 이전 데이터 유지**다.

외부 사이트 실패는 내부 버그가 아니므로 traceback 수준으로 취급할 필요가 없다. 동시에 완전 무음 처리도 바람직하지 않다. 따라서 “짧은 경고 + 기존 상태 유지 + 재시도”가 가장 균형이 좋다.

## 공식 STOM_V 설계

### 1. webcrawling 정책

`utility/webcrawling.py`에는 다음 정책을 적용한다.

- 네트워크 예외는 각 수집 함수 내부에서 처리한다.
- 실패 시 `dict_data`는 기존 값을 유지한다.
- 실패 시 시스템로그에는 한 줄만 남긴다.
- 로그 포맷은 예외 타입과 대상만 보이게 짧게 유지한다.
  - 예: `바이낸스 데이터 갱신 실패: ReadTimeout`
  - 예: `네이버 지수 갱신 실패: ConnectionError`
- 같은 종류의 실패는 일정 시간 동안 중복 출력 억제를 둔다.
- 성공하면 실패 억제 상태를 해제한다.
- 실패하더라도 홈 데이터 갱신 주기 전체가 멈춘 것처럼 보이지 않게 완료 카운터 정책을 유지한다.

### 2. telegram_bot 정책

`utility/telegram_bot.py`에는 다음 정책을 적용한다.

- 봇 초기화 실패와 polling 중 실패를 구분한다.
- 네트워크 계열 실패는 traceback 대신 한 줄 경고로 남긴다.
- 토큰/아이디 미설정과 네트워크 실패를 별도로 구분한다.
- 재시작 로직은 유지하되, 연결 실패 때문에 시스템로그가 장문 traceback으로 도배되지 않게 한다.
- 가능하면 라이브러리 내부 traceback이 그대로 노출되지 않도록 상위 래퍼에서 정리한다.

### 3. 로그 레벨 원칙

- 내부 논리 오류: traceback 유지
- 외부 네트워크 오류: 경고 1줄

이 기준을 명확히 나누어야, 실제 코드 버그는 계속 드러나고 외부 장애는 운영 친화적으로 보인다.

## 다운스트림 전파 설계

### 전파 원칙

- 공식 `STOM_V`를 원본으로 삼는다.
- 공식 fix 브랜치에서 수정과 검증을 먼저 끝낸다.
- 이후 `2U -> 2U_C -> wt-dev / research` 순으로 전파한다.

### 워크트리별 적용 방식

#### STOM_Version_2U

- 공식과 가장 가까우므로 동일 diff에 가깝게 반영한다.
- 가능하면 공식 변경을 기준으로 최소 수정한다.

#### STOM_Version_2U_C

- `2U` 반영 이후 cherry-pick 또는 최소 충돌 수정으로 반영한다.
- CLI/커스텀 차이 때문에 의미상 동일 정책만 맞추면 된다.

#### wt-dev

- 공식 수정과 동일 정책을 유지하되, 이미 변경된 런타임 구조를 존중한다.
- `backQ`, 텔레그램 큐 계약, QThread 처리 등 최근 반영분과 충돌하지 않는지 확인한다.

#### research/init

- `wt-dev`와 유사한 구조를 따르므로 동일 정책 반영 대상으로 본다.
- 공식 diff를 그대로 넣기보다 `wt-dev` 반영 결과 기준으로 맞추는 편이 더 안전할 수 있다.

## 검증 기준

### 공식 STOM_V

- 단위 테스트
  - 크롤링 실패 시 기존 데이터 유지
  - 경고 메시지 형식 검증
  - 중복 경고 억제 검증
  - 텔레그램 네트워크 실패 시 traceback 대신 경고 처리 검증
- 정적 검증
  - `py_compile`
- 수동 런타임 검증
  - 네트워크 차단 또는 타임아웃 상황에서도 traceback 대신 경고만 보이는지 확인
  - 백테스트 완료 로그가 외부 예외에 가려지지 않는지 확인

### 다운스트림

- 공식 반영 후 동일 정책 유지 여부 확인
- 최소 회귀 테스트
  - 경고 처리 테스트
  - `py_compile`
- 기존 sync 가드와 충돌 없는지 확인

## 리스크

### 1. 과도한 무음화

예외를 너무 숨기면 실제 장애를 놓칠 수 있다. 따라서 완전 무음이 아니라 “짧은 경고”가 필요하다.

### 2. 과도한 공통화

공식과 워크트리 구조가 다를 수 있으므로, 전파 시 코드 모양보다 정책 일치가 중요하다.

### 3. 로그 억제 부작용

중복 억제를 잘못 설계하면 사용자가 장애 지속 여부를 알 수 없다. 억제는 “같은 오류를 과도하게 반복하지 않는 정도”로 제한해야 한다.

## 구현 후 기대 효과

- 백테스트 정상 완료 로그가 외부 네트워크 traceback에 묻히지 않는다.
- 홈탭 데이터/텔레그램 장애가 발생해도 프로그램 전체가 실패한 것처럼 보이지 않는다.
- 공식 `STOM_V`에서 먼저 품질 기준을 고정하고, 이후 워크트리로 일관되게 전파할 수 있다.
