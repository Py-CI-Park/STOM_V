# Cross-Worktree Runtime Regression Audit Design

## 목적

`STOM_V.wt-dev`에서 확인된 런타임 회귀를 한글로 정리하고, 공식 워크트리 `STOM_Version_2`를 제외한 나머지 워크트리에도 동일한 결함이 존재하는지 체계적으로 감사한다. 감사 결과는 단순 참고가 아니라, 각 워크트리별로 `반영 필요`, `반영 불필요`, `추가 조사 필요`를 명확히 판정할 수 있어야 한다.

## 배경

이번 회귀는 `V2.70 ~ V2.73` 공식 업데이트 반영 과정에서 발생한 구조적 불일치 성격이 강하다. 실제로 `wt-dev`에서는 다음 문제가 연쇄적으로 드러났다.

1. 지수차트 삭제 후 `ui_mainwindow.py`, `ui_process_kill.py`에 잔여 참조가 남아 import 및 종료 경로에서 예외가 발생함.
2. `utility.static` 리팩터링 후 `summer_time`, `get_profile_text` 같은 호환 심볼이 빠져 키움 관련 런타임 import가 깨짐.
3. `utility.webcrawling.WebCrawling`이 `QThread` 기반으로 바뀌었는데 `ui_mainwindow.py`는 계속 `Process(target=WebCrawling, ...)`로 실행하여 홈탭 데이터가 UI에 전달되지 않음.
4. 종료 경로에 존재하지 않는 `qtimer0` 참조가 남아 추가 예외를 일으킴.

이 문제들은 "공식 업데이트를 반영하는 비공식 워크트리에도 반복적으로 재유입될 수 있는 결함"으로 간주한다.

## 목표

1. `wt-dev`에서 발생한 문제들의 증상, 원인, 해결책, 검증 결과를 한글로 문서화한다.
2. `STOM_Version_2`를 제외한 워크트리 `STOM_Version_2U`, `STOM_Version_2U_C`, `research/init`를 감사한다.
3. 각 워크트리에서 동일 문제가 실제로 존재하는지 근거 기반으로 판정한다.
4. 동일 문제가 확인된 워크트리만 최소 수정으로 반영한다.
5. 어떤 워크트리에 왜 반영했는지, 왜 반영하지 않았는지 추적 가능한 결과를 남긴다.

## 비목표

1. 공식 워크트리 `STOM_Version_2` 수정.
2. 이번 회귀와 무관한 리팩터링, 스타일 정리, 일반 품질 개선.
3. 추측성 일괄 패치.

## 감사 대상과 우선순위

1. `STOM_Version_2U`
   공식 업데이트를 직접 받아오는 계열이므로 우선 확인 대상이다.
2. `STOM_Version_2U_C`
   커스텀 브랜치지만 공식 업데이트 동기화 영향권이므로 우선 확인 대상이다.
3. `research/init`
   목적이 다르므로 동일 파일, 동일 경로, 동일 참조가 실제 존재할 때만 반영 대상으로 본다.

## 기준 결함군

감사는 아래 결함군만 대상으로 한다.

1. 지수차트 삭제 후 잔여 참조
   `ui.ui_draw_jisuchart`, `DrawRealJisuChart`, `show_jisu`, `dialog_jisu`
2. `utility.static` 호환 심볼 누락
   `summer_time`, `get_profile_text`
3. 홈탭 데이터 전달 경로 불일치
   `WebCrawling(QThread)` 구조와 `ui_mainwindow.py`의 실행 방식 불일치
4. 종료 경로 잔여 참조
   `qtimer0`처럼 현재 `MainWindow`에 존재하지 않는 속성 참조

## 실행 절차

### 1. 기준 사례 정리

`wt-dev`에서 발생한 문제를 다음 형식으로 한글 문서에 정리한다.

- 증상
- 발생 조건
- 직접 원인
- 코드 레벨 원인
- 해결 내용
- 검증 명령과 결과

### 2. 타 워크트리 감사

각 워크트리에서 아래 순서로 확인한다.

1. 관련 파일 존재 여부 확인
2. 정적 참조 검색
3. 필요 시 최소 import 검증 또는 짧은 실행 검증
4. `존재`, `미존재`, `판정 유보`로 분류

### 3. 반영 판정

다음 기준으로 판정한다.

- `반영 필요`
  동일 결함이 실제로 존재하고, 현재 브랜치 동작을 깨거나 다음 공식 반영 때 반복 가능성이 높은 경우
- `반영 불필요`
  해당 파일/참조/실행 경로가 없거나 이미 해결된 경우
- `추가 조사 필요`
  정적 흔적은 있으나 실행 경로가 달라 즉시 반영 근거가 부족한 경우

### 4. 반영 방식

반영이 필요한 워크트리는 각 워크트리에서 개별 수정과 개별 커밋으로 처리한다. 공통 원인은 문서에 공유하지만, 커밋 히스토리는 워크트리별로 분리한다.

## 문서 산출물

최종 한글 문서에는 아래 표가 포함되어야 한다.

| 워크트리 | 동일 문제 존재 여부 | 근거 | 반영 필요 여부 | 실제 반영 여부 |
| --- | --- | --- | --- | --- |
| STOM_Version_2U | 감사 예정 | 감사 후 기록 | 감사 후 판정 | 감사 후 결정 |
| STOM_Version_2U_C | 감사 예정 | 감사 후 기록 | 감사 후 판정 | 감사 후 결정 |
| research/init | 감사 예정 | 감사 후 기록 | 감사 후 판정 | 감사 후 결정 |

## 검증 계획

`wt-dev` 기준 검증은 아래를 포함한다.

1. `python -m pytest tests/unit/ -q`
2. `python -c "import importlib; importlib.import_module('ui.ui_mainwindow')"`
3. 키움 관련 import 검증
4. 짧은 `python stom.py` 실행으로 즉시 traceback 부재 확인
5. 홈탭 신호 경로 검증

타 워크트리 감사는 변경 전 읽기 전용 검증을 우선한다. 실제 반영이 필요한 워크트리만 수정 후 해당 워크트리에서 다시 최소 검증을 수행한다.

## 커밋 전략

1. 현재 단계에서는 설계 문서만 단독 커밋한다.
2. `wt-dev`의 실제 코드 수정 커밋은 문서 리뷰 후 별도 커밋으로 남긴다.
3. 다른 워크트리 반영이 발생하면 워크트리별로 독립 커밋을 만든다.
4. 스테이징은 항상 명시적 파일 지정으로 수행한다.

## 리스크와 대응

1. 공식 업데이트 계열과 연구 워크트리의 성격 차이
   `research/init`은 실제 동일 결함이 확인될 때만 반영한다.
2. 문자열 검색만으로는 런타임 경로를 완전히 보장하지 못함
   필요한 경우 import 검증 또는 짧은 실행 검증으로 보완한다.
3. 여러 워크트리에 기계적으로 같은 패치를 넣을 위험
   반영 전 `존재 근거`를 확보한 뒤에만 수정한다.

## 승인 후 다음 단계

이 설계가 승인되면 다음 순서로 진행한다.

1. 설계 문서 커밋
2. `wt-dev` RCA 문서 작성 및 코드 수정 커밋 정리
3. 타 워크트리 감사
4. 반영 필요 워크트리만 수정
