### 1.2 근본원인 (정직한 결론)
1. **이름표 충족 패치**: 각 요구를 "최소 추가물(fold·밴드·바)"로 environ하고 릴리스명은 요구 전체를 딴 것 — 요구의 **본질(구조 재설계)** 대신 **표면(라벨)** 을 구현.
2. **검증 척도 오선정**: scrollHeight·hero px 같은 좁은 수치는 통과시켰지만, 사장님 실제 판단 기준인 **"한눈에 여러 과정"·"단계가 나와 함께 진행"** 을 수치화하지 않음(스테이지 뷰 존재 여부·첫 화면 동시 노출 과정 수).
3. **데이터 없는 화면을 완료로 계상**: Catalog·HoF는 컴포넌트만 있고 실데이터가 안 보임(DB gitignore) — 화면 검수 기준으론 미완.
4. **속도 우선 압박 해석**: "5.7까지 모두 진행"을 "모든 릴리스 라벨 소화"로 해석 — 각 릴리스의 완성 기준을 계획 §대로 지키지 않음.

## 4. 운영 규칙 (재발 방지)
1. **릴리스명 = 실변경**: 요구 라벨을 딴 릴리스는 그 요구의 수용 기준 전부를 충족해야 merge. "부분"이면 릴리스명에 (부분) 명기.
2. **화면 검수 게이트**: 수치 통과 + **사장님 실화면 검수** 를 각 단계 완료 조건에 포함. 미달 시 동일 단계 반복.
3. **데이터 없는 화면은 미완**: 컴포넌트 존재가 아니라 "실데이터가 보인다"가 완료 기준.
4. 점수표는 각 단계 merge 시 갱신·커밋(이 문서 §2).
