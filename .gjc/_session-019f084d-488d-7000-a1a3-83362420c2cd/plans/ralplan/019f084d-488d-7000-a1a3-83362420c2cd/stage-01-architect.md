## Summary
The Planner artifact hybrid-shell direction is architecturally sound: the current `/ui/remodel/` artifact is a visual/static preview, while the existing React/FastAPI dashboard already contains the executable contracts for condition AI, backtest, and chart replay. I recommend proceeding with the hybrid approach, but with WATCH status because implementation must first pin the remodel route namespace/bootstrap and safety-export semantics explicitly; otherwise the reused production app can navigate out of `/ui/remodel/` or inherit production export behavior without the remodel-specific guardrail.

## Analysis
Planner compliance is strong at the product level. The plan preserves `/ui/evolution`, `/ui/backtest`, and `/ui/chart-replay`, keeps `/ui/remodel/` as the remodel entry, rejects greenfield duplication, forbids unlabeled mocks, and carries the safety constraints: research-only, no live order, no broker login, no account/account trading, no hidden automatic production export.

File-backed evidence supports the main decision:
- Current backend route preservation is real: `ai_strategy_loop/dashboard/app.py` defines explicit existing UI handlers for `/ui/evolution`, `/ui/backtest`, and `/ui/chart-replay` before static mounts (`app.py:2694-2711`), then mounts `/ui/remodel` before `/ui` (`app.py:3405-3414`). This matches the Planner route-preservation constraint.
- The current remodel is not a production replacement: `frontend/remodel/src/data.js` declares dummy data, and `frontend/remodel/src/app.js` still renders from `DATA.*` while only bridging `/health`, `/status`, `/runs`, and `/ws` (`app.js:160-201`, `app.js:348-355`, `app.js:374-388`). The scorecard/parity docs rate it about 55/100 existing parity and identify backtest/replay/state-machine gaps.
- The production dashboard already has the mature surfaces the plan wants to reuse: `app.jsx` imports and mounts `BacktestTab` and `SimulationTab` (`app.jsx:23-25`, `app.jsx:359-366`), backtest components consume `/bt/health`, `/bt/strategies`, `/bt/run`, `/bt/ws_job`, `/bt/result`, compare/overlay/portfolio/report paths (`bt-tab-root.jsx:111-245`, `bt-tab-run.jsx:137-281`, `bt-tab-analysis.jsx:93-451`), and replay consumes `/sim/health`, `/sim/days`, `/sim/stocks`, `/sim/signals`, and `/sim/ws` (`sim-tab-root.jsx:1-263`).
- Backend API contracts exist rather than needing invention: `backtest_api.py` exposes `/bt/health`, strategy CRUD/validation, variables, self.vars preview, BackFinder preflight, run/job/result/evo/analysis/compare/overlay/portfolio/report/ws routes (`backtest_api.py:252-1969`), while `simulation_api.py` exposes `/sim/health`, `/sim/days`, `/sim/demo`, `/sim/stocks`, `/sim/signals`, and `/sim/ws` (`simulation_api.py:127-683`).
- Safety is already partly pinned in the remodel preview tests: `tests/unit/test_dashboard_remodel_static.py` asserts the live bridge markers, absence of `final_approval`, and no live-order/broker/account controls (`test_dashboard_remodel_static.py:60-88`). Reusing production components must preserve or consciously replace that guard.

Spec compliance: the plan solves the requested problem at the right layer. It treats the production dashboard as the executable specification, does not remove existing routes, and postpones promotion until page-by-page functional and visual evidence closes the scorecard. It does not add unrelated broker/account/live-trading behavior.

Architecture: Option A is the right default because backtest and replay are not just screens; they are state machines with job tracking, websocket semantics, result libraries, chart engines, and handoffs. The plan correctly avoids rewriting those from the vanilla prototype. The main risk is not the decision, but the seam between the production app `/ui/*` assumptions and a remodel-specific `/ui/remodel/*` ownership model.

Strongest steelman antithesis to the hybrid-shell approach: a clean greenfield remodel app could define a typed API client, route namespace, CSS scope, accessibility model, and research-only safety policy from first principles. It would avoid carrying legacy global window exports, bundle-order constraints, hard-coded `/ui` paths, broad shared CSS, and the production `final_approval` export path into a design-led replacement. That argument is real. It loses here because the current scorecard shows the missing value is not visual composition; it is mature production behavior in backtest/replay/condition-analysis state machines. Recreating those state machines would multiply failure modes and likely preserve mocks longer.

Deliberate-mode principles: the principles are coherent and mostly confirmed by evidence. `Reuse production logic first`, `No mock masquerade`, `Preserve existing routes`, `Keep safety boundaries explicit`, and `Completion requires functional plus visual evidence` align with the inspected code and docs. The only principle-level tension is that `research-only` plus `reuse production components` can accidentally inherit `final_approval` export behavior from `app.jsx`/`app.py`; that is acceptable only if the implementation makes the human-gated export boundary explicit or disables it in remodel until approved.

## Root Cause
The root architectural problem is the gap between two valid systems: the production dashboard has real behavior but assumes `/ui/*`, shared global CSS, bundled React entrypoints, and existing export semantics; the remodel preview has the desired IA/visual language but is a dummy-data no-build static app. A safe plan must define the route, bundle, CSS, and safety adapter between those systems, not just say to mount production components inside the remodel shell.

## Findings
1. **MEDIUM — Remodel route namespace/deep-link contract is underspecified.** `ui-contract.jsx` hard-codes canonical paths under `/ui/evolution`, `/ui/backtest`, and `/ui/chart-replay` (`ui-contract.jsx:65-116`), and `app.jsx` replaces/pushes browser history to those canonical paths (`app.jsx:140-149`, `app.jsx:180-183`). If the production `App` is bootstrapped directly under `/ui/remodel/`, it can navigate out of remodel ownership. Fix: before implementation, add an explicit remodel routing addendum: either hash/query routing under `/ui/remodel/` or prefix-aware `dashboardPathFor`/`dashboardRouteFromLocation` plus backend catch-all tests for refresh/deep links.
2. **MEDIUM — React bootstrap/build strategy needs a concrete entrypoint.** The production UI now uses `webui-build` and content-hashed `frontend/bundle/app.js`/`stom-ui.js`; the remodel preview uses no-build `src/data.js` and `src/app.js`. Fix: choose one implementation path before coding: a dedicated `RemodelApp` bundle emitted by `webui-build`, or reuse `app.js` with an explicit no-auto-mount/remodel mount adapter. The plan should require manifest/hash updates and avoid raw JSX/runtime-Babel or a second parallel renderer.
3. **MEDIUM — Safety-export semantics must be pinned when production components are reused.** The preview tests currently assert no `final_approval` path in remodel, while the production dashboard contains an explicit `final_approval` websocket action that writes through `export_winner` to production `strategy.db` after human approval (`app.py:3424-3464`). Fix: define whether remodel disables export entirely during research-only replacement work or reuses the existing modal with explicit human confirmation, visible audit separation, and source/DOM guards proving no hidden automatic export.
4. **MEDIUM — CSS token bridge can regress preserved routes if not scoped.** Production `styles.css` uses `--bg-0`, `--bg-1`, `--line-1`, `--ink-*`, etc.; remodel `theme.css` uses `--bg`, `--panel`, `--border`, `--text`, and overlapping semantic colors. Fix: use a namespaced remodel shell or CSS layer/token mapping, then require screenshot controls for `/ui/evolution`, `/ui/backtest`, `/ui/chart-replay`, and `/ui/remodel/` on every pass.
5. **LOW — E2E verification must prove behavior, not just static route serving.** Existing remodel tests cover route serving, IA labels, bridge markers, and forbidden controls, but the Planner correctly calls for browser E2E of backtest job lifecycle, replay WS controls, audit submit, inspector, and settings. Fix: keep this as a non-negotiable execution gate with deterministic fixtures/read-only DB overrides and no operating DB writes.

## Recommendations
1. Add a pre-implementation route addendum: define the remodel URL scheme for common shell, condition subtabs, backtest, replay, settings, inspector, and modals. Include tests for direct refresh/deep links and for preservation of the three existing routes.
2. Add a build/bootstrap addendum: specify the `webui-build` entry, output files, manifest/hash update, and whether `App` is reused with a remodel adapter or a new `RemodelApp` composes production child components.
3. Add a safety addendum: explicitly decide `final_approval` behavior in `/ui/remodel/`; ensure no broker/login/account/live-order controls and no hidden export path; require source/DOM assertions.
4. Treat CSS as an adapter, not a replacement: map tokens, scope remodel classes, and avoid global resets that affect the preserved routes.
5. Keep the Planner execution sequencing, but make backtest/replay parity the first hard gates after shell/bootstrap because those are the largest existing-dashboard parity deficits.

## Trade-offs
| Option | Benefit | Cost/Risk | Synthesis |
|---|---|---|---|
| Hybrid shell with production components | Fastest path to real parity; preserves `/bt/*`, `/sim/*`, condition APIs and tested state machines | Route prefix, build entry, CSS bridge, and export semantics must be adapted | Chosen approach remains correct, with required adapter addenda before implementation |
| Greenfield rewrite of remodel prototype | Clean route/CSS/type/safety model; fewer legacy globals | Reimplements deep backtest/replay/analysis state machines; high mock-retention risk | Use only for visual shell primitives, not functional engines |
| Iframe/embed old pages | Low initial integration cost; isolates CSS | Not a standalone replacement; brittle focus/routing/theme and hides gaps | Reject as the Planner did |
| Disable all export in remodel | Strongest research-only safety | Diverges from existing approval workflow and may reduce parity | Acceptable until final promotion; if export is enabled, it must reuse explicit human gate and audit separation |
