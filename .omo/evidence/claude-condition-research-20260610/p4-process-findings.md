# 전체 프로세스 점검 발견사항 (2026-06-10, 실측 기반)

6/5 방향성 검토(§3 파이프라인 해부)의 진단을 전제로, 이번 실측에서 새로 확인된
프로세스 사실/결함/개선점만 기록한다.

## 1. 확인된 사실 (재현 증거)

- **zero-LLM 평가 경로 정상**: seed_buy/seed_sell + max_generations=1 경로와
  WarmBacktestSession(prepare 1회+run N회)이 LLM 없이 완전 동작.
  스모크 prepare 62초(2025Q1, 814종목, 8엔진), run당 22~23초(시드/gen4).
- **gen4 과적합 실측 재확인**: 6/4 동결 후보 gen4는 2025Q1 서브윈도우에서
  -141,200원/5거래. 같은 분기 인간 시드는 +2,023,670원/24거래/MDD 4.98.
  train 전체(2023-25)에서 +1.15M였던 후보가 train의 부분 구간에서도 음수 —
  "train 점수가 서브윈도우 일반화도 보장하지 않는다"는 직접 증거.
- **배치 run의 대시보드 호환**: record_generation 계약만 지키면 비-루프 도구의
  run도 /runs, /run_state에 정상 표시된다(분석/관측 기능 재사용 가능).
- **대시보드 분석 기능 정상**: 관련 단위테스트 318개 통과, live GET
  (/health /runs /run_state /adaptive_timing /config/spec /research_docs
  /research_criteria) 모두 200.

## 2. 새로 발견된 프로세스 결함/위험

### 2.1 전략의 "틱당 계산 예산"이 어떤 게이트에도 없다 (실측: C1 타임아웃)
- v5.0 리포트식 복합 전략(파생변수 ~20개를 모든 틱에서 선계산)은 구조적으로
  유효(컴파일/스코프/범주 게이트 전부 통과)하지만 **엔진에서 300초 타임아웃**.
  (시드 22초 대비 >15배. 시드/gen4는 싼 게이트로 95%의 틱을 먼저 자른다.)
- 함의: LLM 생성 루프에서도 동일 — 생성기가 "복잡하지만 valid"한 전략을 내면
  세대 전체가 타임아웃으로 소모된다. PRE-SAVE 게이트(범주 수)는 폭만 보고
  **계산 비용**은 보지 않는다.
- 개선 후보(토글, 기본 OFF): ① 프롬프트에 "선게이트 후계산(지연 계산)" 구조
  지침 추가, ② PRE-SAVE에 '게이트 앞 호출형 함수 수' 상한(정적 AST 카운트).
- 이번 사이클의 대응: C1을 지연계산 구조(C1B)로 재작성(시그널 동일).

### 2.2 선택기-기록 계약의 취약성 (fullmatch 결합)
- sparse_positive_v1의 sparse 버킷 판정은 gate_reason 문자열
  `daily_avg_trades X < min_daily_trades Y` **전체일치(fullmatch)**다.
  reason에 접두사/접미사를 붙이는 어떤 도구든 버킷 분류가 조용히 깨진다.
  (이번에 배치 도구 1차본이 라벨 접두사를 붙여 발견; train 전 수정 완료.)
- 개선 후보: reason 원문 보존을 record 계약으로 문서화하거나, 버킷 판정을
  문자열이 아닌 구조화 필드로 옮기는 것(후속 과제, 이번 사이클 범위 밖).

### 2.2b ⭐ 타임아웃의 진짜 지배 변수는 매도식이었다 (11회 실측, 완벽 분리)
- 최초 가설(매수측 선계산/도달률)로 B판 재구조화·니치 축소를 거듭해도 타임아웃이
  지속 → 교차 분석 결과 **매도 전략이 완벽한 분리 변수**:
  - 타임아웃 11건 전원: `S_DYN`/`S_TREND` 사용 — 공통으로 `고가미갱신지속틱수()`
    (마지막 신고가까지 역방향 스캔 = 비유계 O(history)) + 보유 틱당 윈도우 호출 다수.
  - 고속(21~34s) 전원: 시드매도/gen4매도/`S_FAST` — 미갱신류 호출 없음.
- 메커니즘: 보유 종목의 **모든 틱**에서 매도식이 평가되므로, 매도식의 비싼 호출은
  (보유 종목 수 × 보유 시간)에 곱해져 매수측보다 훨씬 크게 터질 수 있다.
- 검증: 동일 매수(C2C/C9) × 윈도우 호출 0개 `S_DYN2` 교차 스모크(smoke-d)로 확인.
- LLM 루프 함의: 매도 프롬프트/PRE-SAVE에 "미갱신류·장윈도우 함수 사용 시 보유시간
  상한 필수" 또는 "매도식 윈도우 호출 수 상한" 가이드가 필요(토글 후보).

### 2.3 warm run 시간의 데이터 길이 비례성 (train 설계 제약)
- per-run 시간 ≈ 데이터 일수에 비례. 3년 train은 2025Q1 스모크의 ~12배.
  스모크 150초 초과 후보는 train(타임아웃 1200초)에서 잘릴 가능성이 높다.
  → 정책에 "스모크 >150초면 지연계산 재작성 후 재스모크"를 사전선언로 추가.
