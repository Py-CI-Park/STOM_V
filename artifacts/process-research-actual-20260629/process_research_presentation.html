STOM 조건식 연구 프로세스 개선 설계

이번 업데이트의 핵심은 STOM 변수/규칙 전체 포함, 이전 매수·매도 조건식 전문 포함, 백테스트 1회 이후 2~3개 이상의 방향성 후보를 동시에 생성·평가, 그리고 분석 카드 기반 반복 연구입니다. 목표는 프로세스 통과가 아니라 실제로 더 좋은 조건식을 만들 확률을 높이는 것입니다.

1. 한 장 요약

맞음

사장님 걱정은 핵심 병목을 정확히 짚었습니다. 좋은 조건식은 프롬프트에 들어가는 연구 컨텍스트 품질이 좌우합니다.

전체

strategy.txt, rules.txt, system prompt, variables, forbidden, 예제까지 가능한 한 포함해야 합니다.

2~3+

백테스트 1회 후 후보 1개가 아니라 서로 다른 가설 후보 2~3개 이상을 동시에 만들고 평가하는 방식이 타당합니다.

공백

현재 process-research는 다중 후보 백테스트는 있지만, 풍부한 LLM prompt 기반 다중 후보 생성은 아직 약합니다.

결론: 다음 개선은 “후보 수 증가”가 아니라 백테스트 분석 → 분석 카드 → 풍부한 Prompt Context Pack → 서로 다른 2~3개 이상 후보 생성 → 공식 백테스트 비교의 폐루프를 만드는 것입니다.

6. 하나의 백테스트 이후 2~3개 후보 동시 생성/평가

현재 존재하는 것

  • cli/research_loop.py에는 후보 여러 개를 선택하고 순차적으로 공식 백테스트하는 구조가 있습니다.
  • 최근 실제 실행에서도 4개 후보가 공식 백테스트까지 완료됐습니다.
  • 즉 “여러 후보를 평가하는 실행 틀”은 이미 있습니다.

부족한 것

  • 최근 process-research 후보는 LLM이 풍부한 컨텍스트를 보고 만든 후보가 아니라 non_llm_expression_candidate였습니다.
  • 후보들이 서로 다른 가설 2~3개로 명확히 갈라진 것이 아니라 단순 quantile/필터 후보에 가깝습니다.
  • 따라서 “동시 평가 틀은 있음, 고품질 동시 생성은 부족”이 정확한 진단입니다.

권장 후보 팩 구조

후보역할생성 지시평가 포인트
A보수적 Repair부모 buy/sell 유지, 가장 큰 실패 원인 1개만 수정MDD 개선, 거래수 유지
B공격적 Repair같은 부모에서 다른 수정축. 예: 시간/시총/체결강도 중 하나만 변경수익 개선, 과매매 방지

퀀트 판단: 하나의 백테스트에서 후보 1개만 만드는 것은 정보 사용 효율이 낮습니다. 같은 분석 결과에서 서로 다른 가설 2~3개를 만들고 같은 공식 엔진으로 평가해야 탐색 속도와 학습 품질이 올라갑니다.

7. 분석 카드란 무엇인가

분석 카드는 “백테스트 결과를 다음 조건식 생성으로 넘기기 위한 연구 메모의 표준 단위”입니다. 사람이 백테스트 결과를 보고 다음 실험을 정리하는 카드라고 보면 됩니다.

무엇을 설명하나

  • 어떤 후보/부모를 분석했는지
  • 어디서 손익이 났는지
  • 실패 원인이 무엇인지
  • 다음 후보가 무엇을 고쳐야 하는지

왜 필요한가

  • LLM이 감으로 조건식을 만들지 않게 함
  • 한 번에 하나의 원인만 고치게 함
  • 후보 생성 이유를 나중에 추적 가능하게 함
  • 성과가 없을 때도 학습을 남김

좋은 분석 카드 조건

  • root-cause가 명확함
  • segment contribution이 있음
  • 수정축이 하나임
  • expected effect와 risk가 있음
  • 승격 권한을 주장하지 않음

분석 카드 필드 예시

{
  "analysis_card_id": "baseline_902_card_001",
  "parent_buy_id": "Tick_B_902_905_Update_2",
  "parent_sell_id": "Tick_S_902_905_Update_2",
  "root_cause": "09:00~09:05 중소형 급등 이후 되돌림 구간에서 give-back 손실이 큼",
  "segment_contribution": {
    "bad_segments": ["09:00~09:05 / 중소형 / 등락률 6~9%"],
    "good_segments": ["09:06~09:15 / 거래대금 증가 / 체결강도 유지"]
  },
  "mutation_axis": "time_window_or_exit_trailing_only",
  "expected_effect": "거래수는 10~20% 감소하되 MDD와 give-back 감소",
  "risk_note": "너무 좁히면 daily trades가 0.5 미만으로 하락 가능",
  "promotion_authority": false
}

8. 실제 실행 증거: 무엇을 돌렸고 어디서 막혔나

1차: archived seed 이름 사용
결과: baseline_run error. 현재 strategy.db에 과거 GATE 전략명이 없어 실패했습니다.
2차: 현재 DB 전략명 사용
기준선 전략 Tick_B_902_905_Update_2 / Tick_S_902_905_Update_2. baseline 백테스트는 성공했지만 default 분석 기준에서 후보가 0개였습니다.
3차: archived CSV strict analysis
과거 기준선 CSV를 사용했지만 strict 기준에서는 여전히 후보 0개였습니다.
4차: relaxed diagnostic pass
후보 4개가 생성되어 공식 백테스트까지 완료됐습니다. 이 실행이 실제 개선 프로세스 검증의 핵심 증거입니다.

default 결과

0 후보

분석 기준이 후보화를 막았습니다.

relaxed 결과

4 후보

프로세스가 end-to-end로 실행됐습니다.

승격 결과

0 통과

아직 기준선을 이긴 후보는 없습니다.

12. 구현 관측 페이지 — 무엇을 화면에서 봐야 하나

Research Pack / Branch Tree

context_pack_id, context_pack_sha256, full STOM source 포함 여부, 250k budget 추정치, 그리고 기준선→분석카드→후보팩→공식백테스트→research-only 랭킹 흐름을 한 화면에 보여줍니다.

Candidate pack / Analysis cards

후보 2~3개 이상, 각 후보의 hypothesis_id, mutation_axis, novelty, expected effect, risk note, 분석 카드의 root-cause/segment contribution/Insight Score를 같이 봅니다.

Prompt receipts / Fallback

프롬프트 버전, prompt score, strict validation, downstream official backtest result가 receipt에 남고, deterministic filter-only 후보는 diagnostic_deterministic_candidate_fallback으로만 표시되며 prompt credit은 0입니다.

/skill:ralplan --deliberate "STOM 조건식 연구 프로세스 개선을 위한 상세 실행 계획을 작성한다. 목표는 프로세스 통과가 아니라 실제로 더 좋은 조건식을 만들 확률을 높이는 것이다. STOM 변수/규칙은 요약이 아니라 utility/ai_agent/strategy.txt, utility/ai_agent/rules.txt, system_prompt, variables_reference, forbidden, 예제 구조를 250k prompt budget 이내에서 최대한 전체 포함한다. 3가지 연구 모드인 기존 시드 repair, 신규 discovery, promotion-review 전체에 공통 적용되는 Research Prompt Context Pack을 설계한다.
